# HCB Lua-like 参数编号偏移错误说明

## 1. 结论摘要

在 [`hcb_ir_core.py`](../../02_tools/hcb_ir/hcb_ir_core.py:560) 的 Lua-like 导出逻辑中，曾存在一个系统性的参数编号偏移错误：

> 对函数体内的 `push_stack -N` / `pop_stack -N`，导出器把第一个真实外部入参命名成了 `a1`，而不是 `a0`。

该问题只影响 **Lua-like 文本中的参数名称**，不影响：

- 原始 HCB 字节；
- `.ir.json` 中记录的 `push_stack` 原始负索引；
- CFG、跳转地址和函数边界；
- HCB 重新组装时使用的负索引字节值。

换言之，这是一个**反编译可读层的命名错误**，不是 HCB 字节码本身被修改或解析错位。

当前已修正 [`slot_name()`](../../02_tools/hcb_ir/hcb_ir_core.py:560) 的映射逻辑，并修正目标函数 [`f_00055D3D()`](./f_00055D3D逐条反汇编对照.md:1) 的参数结论。

---

## 2. 错误是如何产生的

### 2.1 VM 的负栈索引规则

对于一个有 `args_count` 个显式参数的函数，VM 使用负索引访问外部参数槽。以 9 参数函数为例，正确对应关系是：

| 原始指令 | 实际参数 |
|---|---:|
| `push_stack -10` | `a0` |
| `push_stack -9` | `a1` |
| `push_stack -8` | `a2` |
| `push_stack -7` | `a3` |
| `push_stack -6` | `a4` |
| `push_stack -5` | `a5` |
| `push_stack -4` | `a6` |
| `push_stack -3` | `a7` |
| `push_stack -2` | `a8` |

因此，负索引到参数编号的正确公式是：

```text
abs_i   = -idx - 2
arg_idx = args_count - abs_i - 1
```

也可以直接写成：

```text
arg_idx = args_count + idx - 1
```

前提是 `idx` 为合法的参数负索引。

### 2.2 原来的错误公式

旧实现使用了：

```python
abs_i = -idx - 2
return f"a{args_count - abs_i}"
```

这里少减了 `1`，所以产生了整体右移：

```text
旧映射：-10 -> a1, -9 -> a2, ..., -2 -> a9
正确映射：-10 -> a0, -9 -> a1, ..., -2 -> a8
```

这正是之前许多 Lua-like 反编译文本中出现“函数头只有 `a0..a8`，函数体却读取 `a9`”的根本原因。

## 3. 在 `f_00055D3D` 中的具体影响

[`f_00055D3D()`](Sakura_hcb_ir/Sakura/f_00055D3D.lua:1) 的函数序言是：

```text
init_stack args=9 locals=3
```

因此它有 9 个显式参数，真实参数只能是 `a0..a8`。

该函数中关键负索引的正确解释如下：

| 原始负索引 | 旧错误名称 | 正确名称 | 实际用途 |
|---|---|---|---|
| `-10` | `a1` | `a0` | dissolve/mask 编号；`0..55` 映射到 `graph/diss00..diss55` |
| `-9` | `a2` | `a1` | 转场持续时间，通常单位为 ms |
| `-8` | `a3` | `a2` | `-1` 特殊模式判断 |
| `-7` | `a4` | `a3` | alpha / dissolve 等待控制 |
| `-6` | `a5` | `a4` | mask dissolve 模式/方向存在性开关 |
| `-5` | `a6` | `a5` | alpha 动画路径控制 |
| `-4` | `a7` | `a6` | 特殊过渡模式兼容开关 |
| `-3` | `a8` | `a7` | 是否强制等待 dissolve |
| `-2` | `a9` | `a8` | 额外等待模式值，`1` 时强制 `DissolveWait(true)` |

因此，旧结论中以下说法均需要按整体左移一位理解：

- “`a1` 是 mask 编号”应改为“`a0` 是 mask 编号”；
- “`a2` 是时长”应改为“`a1` 是时长”；
- “`a9` 是隐式第十参数”应改为“`a8` 是第九个显式参数”；
- “`a0` 本体未读”应改为“真实 `a0` 由 `push_stack -10` 读取，并参与 mask 选择”。

逐条反汇编时，原始的 `push_stack -N` 仍然是最终可靠依据；Lua-like 文本中的参数名只能在修正后的映射下阅读。

## 4. 为什么此前没有立即暴露

这个错误容易被历史资料掩盖，主要有以下原因：

1. **大量调用点使用 `nil` 或固定常量**。即使参数名错一位，代码表面上仍然能读懂。
2. **函数头参数数量与函数体访问名不一致**。例如函数头是 `a0..a8`，函数体出现 `a9`，此前被误判为“隐式第十参数”或“导出器特殊栈槽”。
3. **原始负索引仍然保存在 IR 中**。因此字节、地址和控制流分析没有显著异常，错误只出现在可读化阶段。
4. **早期结论已经引用了错误名称**。后续文档在解释时沿用了这些名称，形成了“将错就错”的稳定术语。
5. **部分函数可能确实存在导出器参数槽表现异常**。这使得真正的整体偏移错误与合法的局部上下文槽、调用约定差异混在了一起。

## 5. 为什么后续分析需要包容历史编号

本错误发现后，不宜简单地对整个 [`hcbtool_test`](.) 目录进行机械字符串替换，原因是历史成果已经大量依赖旧编号：

- 多份逐条反汇编文档已经用旧名称建立了语义解释；
- 后续函数分析、调用链分析和演出结论可能引用了这些旧名称；
- 某些文档讨论的是“导出器显示出来的槽位”，而不是严格的源级参数；
- 某些函数还存在入参数量、调用上下文和隐式栈槽的额外复杂性；
- 机械替换可能把本来正确的局部变量、全局状态或其他函数的参数名一并改错。

因此后续应采取以下兼容策略：

### 5.1 新分析优先使用真实槽位

新的逐条反汇编文档应优先写成：

```text
push_stack -10 -> a0
```

必要时同时保留原始负索引，避免再次依赖可能变化的可读化名称。

### 5.2 历史文档保留原文，增加勘误说明

已经完成且被大量引用的旧文档，不要求全部立即重写。对于这类文档，应在开头或参数章节增加：

```text
本文早期版本沿用了 Lua-like 导出器的参数编号偏移。
文中 a1/a2/... 在涉及 push_stack 负索引时，应按当前勘误整体左移一位理解。
```

### 5.3 需要继续扩展的函数再逐个修正

如果某个旧函数要继续进行参数语义分析、HCB 注入或运行时验证，则应在扩展前先依据：

1. `init_stack args=N`；
2. 原始 `push_stack -N`；
3. 调用点压栈顺序；
4. 函数体内实际使用位置；

重新建立该函数的参数表。

### 5.4 不把所有异常都归因于本错误

修正整体偏移后，仍可能存在：

- 函数实际调用参数数量与 `init_stack` 不一致；
- 调用者使用相邻栈槽传递上下文；
- 导出器对局部槽和参数槽混合命名；
- 某些包装函数读取了调用框架中的额外值。

这些情况需要单独验证，不能一律用“左移一位”解释。
