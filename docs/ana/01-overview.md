# 01 · FVP 引擎总览

> **可信度说明**：本文绝大部分内容基于 `rfvp-0.3.0` 源码、多份民间文档与工具源码的交叉印证，标注为 **[已证实]** 或 **[高可信]**。少数仍有歧义的地方会单独标出。

---

## 什么是 FVP？

FVP（Favorite View Point）是日本视觉小说开发商 FAVORITE 社自研的游戏引擎，用于驱动《樱花萌放》（Sakura, Moyu.）、《星空的记忆》（Hoshi Ori Yume Mirai）等作品。

从部署形态看，一个典型的 FVP 游戏目录包含这些东西：

```
game.exe          ← 原生 Windows EXE，内嵌 VM 与 syscall 实现
Sakura.hcb        ← HCB 字节码脚本，游戏的"程序入口"
graph.bin         ← 立绘/背景/UI 图像资源包
voice.bin         ← 语音资源包
bgm.bin           ← 背景音乐资源包
se_sys.bin        ← 系统音效资源包
graph/            ← （某些版本）松散图像文件目录，优先级高于 graph.bin
movie/            ← OP 等视频，直接以 .wmv 等格式存放
```

FVP **不是**把所有内容打进一个巨大的专有包里。它的核心思路是：

> **EXE（VM 宿主） + HCB（字节码脚本） + BIN/HZC（资源容器） + 外置文件覆盖**

这种组合式架构使它天然具备 patch 友好性：往外置目录放一个文件，就能覆盖包内的同名资源，汉化组和 mod 作者非常喜欢这一特性。

## 启动流程

### 找到 HCB

引擎启动时，在游戏目录里按文件名排序找到**第一个 `.hcb` 文件**，将其作为脚本入口。这意味着：

- 放一个字母序更靠前的 `.hcb`，就能替换原来的主脚本；
- HCB 本质上是"程序的 `main` 入口描述物"。

### 解析 HCB 头部

找到 HCB 后，引擎读取文件尾部的**系统描述区**（`sys_desc_offset` 处开始），获取：

- `entry_point`：主入口函数的代码偏移地址
- `non_volatile_global_count` / `volatile_global_count`：全局变量数量
- `game_mode`：分辨率/窗口模式索引（如 `14 → 1920×1080`）
- 游戏标题字符串
- **syscall 导入表**：把脚本中用到的宿主函数名字一一列出

### 建立 VFS 与启动主线程

- 按资源目录查找规则建立虚拟文件系统（VFS）；
- 以 `entry_point` 为入口，启动**线程 0**（主脚本上下文）；
- 进入每帧循环。

---

## 每帧运行逻辑

FVP 是一个"脚本 VM + 场景/运动系统"并行推进的引擎，每帧大致经历：

```
1. 更新输入状态、推进计时器
2. 场景 on_update
   └─ 推进位移、透明度、缩放、旋转、雪、溶解等动画
3. VM runner
   └─ 遍历所有「可运行」脚本上下文
      └─ 每个上下文持续 dispatch opcode
         └─ 遇到 Wait / Sleep / TextWait / DissolveWait 等则挂起
4. 场景 late_update
   └─ 处理文本逐字显示、文本完成后的线程恢复
5. 渲染 prim / text / texture / movie
6. 重置本帧输入边沿
```

关键点：**HCB 脚本并不直接画图或直接播音**，它更像一组"命令流"——通过 syscall 修改引擎状态（`GameData`），再由场景和渲染系统把状态兑现成画面和声音。

## 四层结构

想彻底理解 FVP 的运行，必须同时搞清楚四层：

| 层 | 内容 | 关键概念 |
|---|---|---|
| **HCB 文件层** | 文件结构、地址修正、函数与控制流 | `sys_desc_offset`、`entry_point`、opcode |
| **VM 执行层** | 栈机、线程/上下文、返回值、条件判断、表操作 | `Context`、`Variant`、栈帧 |
| **Syscall 语义层** | 文本、图像、音频、动画、存档、线程、窗口 | `GameData`、syscall 名 |
| **资源系统层** | BIN、HZC、外置目录、文件名排序、locale | VFS、loose override |

这四层缺一不可。很多人以为"看懂了 pushstring 就看懂了 HCB"，实际上 HCB 里充斥着资源名、控制流跳转、syscall 参数包装，文本只是其中一小部分。

---

## FVP 的线程模型

FVP 的"线程"**不是**操作系统线程，而是**脚本协程（上下文）**。

- 默认有 32 个上下文槽位（ID 0..31）；
- `VmRunner` 每帧只推进处于 `RUNNING` 状态的上下文；
- 上下文可以因以下原因挂起：
  - `WAIT`：计时等待（`ThreadWait`）
  - `SLEEP`：睡眠（`ThreadSleep`，等待被唤醒）
  - `TEXT`：文本逐字显示中（等待玩家点击推进）
  - `DISSOLVE_WAIT`：等待画面转场完成

这是典型的**协作式调度**，不是抢占式多线程。理解这一点对分析复杂的演出脚本非常重要——多个上下文同时运行时，它们是轮流让出执行的，而不是真正并行。

## 资源查找顺序

给定逻辑路径 `folder/name`（如 `graph/bg_school`），VFS 按这个顺序查找：

1. 直接查 `<游戏根目录>/graph/bg_school`（松散文件，最高优先级）
2. 查 `<游戏根目录>/graph.bin` 内名为 `bg_school` 的条目

结论：**松散文件 / 松散目录 > `.bin` 包内条目**。

这意味着：
- 汉化替换图片，只需往 `graph/` 目录放同名文件，不必重封 `.bin`；
- 测试修改时，loose 文件比重封包快得多；
- 原始引擎就有这个特性，不是 patch 技巧，是设计如此。

## Locale 与编码依赖

FVP 原始引擎对**日文 Windows 环境**有深度依赖，不只是"台词显示乱码"那么简单：

| 依赖点 | 影响 |
|---|---|
| `CompareStringA(0x411, ...)` | 文件名排序与查找逻辑 |
| `CreateFontA` / `GetGlyphOutlineA` | 字体枚举与字形提取 |
| Shift-JIS codepage (932) | 脚本与资源名解码 |
| 窗口与菜单 A/W API | 字符串显示与处理 |

把台词改成中文能显示，但资源名解码失败、文件名排序错乱、字体找不到、字形提取崩溃——这些都是 FVP 汉化时实际踩过的坑。

`FVPLoader` 的做法是用 Hook 把这些 API 全部替换为兼容版本，是目前已知最系统的解决方案。
