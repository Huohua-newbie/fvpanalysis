# 13 · 方法篇：call 追踪、断点二分与负栈索引规则

> 置信度：**[已验证]**——以下规则在 rfvp `context.rs` 源码与 1020 个 CG stub 的实测调用中双向确认；与本仓库“HCB Lua-like 参数编号偏移”一文的结论一致，可互为佐证。

## 1. 负栈索引规则（一句话版）

`init_stack args=N` 的函数，`push_stack -(N+1) … push_stack -2` 依次是 `a0 … a(N-1)`；再往下（`-(N+2)` 起）是**调用者栈残留**（通常是上一个 `call` 的返回值 + 更早的值）。

| N=9 示例 | 含义 |
|---|---|
| `-10 … -2` | `a0 … a8` |
| `-11` 及以下 | 调用者残留 |

注意两处易错：

1. **调用者栈会累积**：`call` 不清理实参，所以“某次调用的实参 = 本次 `call` 之前最后压的 N 个值”，而不是函数体内全部压栈值。数压栈必须从 `call` 往回数，遇到上一个 `call` 就停。
2. **字面 Nil 是真 Nil**：调用点 `push_nil` 传进去的，函数里读到的就是 `Nil`，别指望调用框架会填。结合 [`11`](./11-coldstart-boot-globals.md) §5，Nil 在判等里恒为“否”。

## 2. `RFVP_CALL_TRACE`：给 VM 加调用追踪

定位“某段剧本到底走了哪条路”，只看 syscall trace 是不够的（纯计算函数无声）。给 `context.rs::call()` 加三行 env 门控日志：

```rust
// FVP-PREVIEW scratch: call trace (RFVP_CALL_TRACE=1). Not for upstream.
if std::env::var("RFVP_CALL_TRACE").is_ok() {
    log::info!("calltrace: from={} to={}", self.cursor, addr);
}
```

`from` 是返回地址（`call` 指令末尾），`to` 是目标函数入口。配合 syscall trace 的时间戳，即可回答“`332832` 被谁调了几次、每次之后调了谁、哪一次没调 `333826`”这类问题。本案就是靠它锁定“`9611 → 332832` 执行了，但 `333826` 从未被调”。

## 3. `--break-pc` 二分

headless VM 支持“任一 context 的 pc 首次越过 ADDR 即停”（注意是越过不是相等，一个 tick 跑多条指令）。用法：

1. 对可疑函数入口设点，确认“到没到”（如 `333245` 到了、`333349` 第一次是早调用不是目标调用——注意区分**哪一次**调用触发，结合 calltrace 的 `from` 判定）。
2. 沿路设点收窄：`333245(到) → 333349(早调用) → …`，配合调用栈上下文定位分叉。

## 4. 一个完整的定位实例（本案回放）

症状：CG 名已压栈，`GraphLoad(190/191, 有名)` 永不出现，只有 `(191, Nil)` 卸载。

1. calltrace 确认 `666632 → 9611 → 332832` 执行，且每次止于 `338431` 返回之后。
2. 读 `332832` 体：`338431` 之后是变体选择树，读自身参数（调用方给的 Nils）+ 全局量。
3. 逐个推演分支（Nil 在判等恒否）：一路走到 `333282` 的 `global1950 ∈ {0,1,2,3}` 四连判等——冷启动全 Nil，全灭 → `jmp 333779` 死路。
4. `--set-global 1950 0` 重跑：`graph_vis/KURO_e011a1/b2/c2/d2/e2` 全系加载。结案。

## 5. 待验证 / 注意事项

- `call '4'` 这类小地址调用（本案 `666641` 处，实为等待类共享子程序）：反汇编器按地址显示，初见容易误判，属正常。
- `push_stack` 负索引超出参数范围时读到的是残留值而非报错，写逐条解析文档时建议同时标注“原始负索引 + 换算后含义”，别只写别名。
