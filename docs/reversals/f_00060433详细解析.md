# [`f_00060433()`](Sakura_hcb_ir/Sakura/f_00060433.lua:1)：`$chara_delete` 立绘离场登记器详解

## 1. 结论先说

根据 [`Sakura.hcb`](Sakura.hcb:1) 的函数体、全调用点、[`$chara_delete`](../../reference/SakuraMoyu_NS/route_haru.ks:9821) 的 KS 对照，以及下游立绘批处理函数，本函数的较准确定位是：

> **为指定立绘槽位登记“删除/离场”状态，并可选地指定该角色消失时的位移方向模式；它本身不立即删资源、不直接执行 alpha/XY/Z motion。**

用户已实测确认的第一个参数“要消除的立绘编号”成立。更具体地说，第一个参数是 Sakura 立绘系统的**逻辑槽位编号**，有效分支为：

```text
0..19、21..24
```

第二参数的结论如下：

> **第二参数是离场位移模式（exit-motion direction/mode），不是等待时间、不是删除开关、不是 Parts 表情编号。**

- `nil` 会被归一化为 `0`：标准删除，不附加位移；
- `1`：沿 **+X** 方向离场；
- `2`：沿 **−X** 方向离场；
- `3/4`：沿 ±Y 方向离场；
- `5..8`：XY 斜向离场；
- `10..17`：包含 Z 偏移的离场模式。

实际执行流程是：

```text
f_00060433(slot, exit_mode)
  ↓
f_0005FE1E(slot, exit_mode)
  ↓
将 G[311 + slot] 置为 3（删除待处理）
将 exit_mode 保存到 G[599 + slot]
  ↓
后续 $chara_disp / f_00060441(...)
  ↓
f_00060795(...)
  ↓
MotionAlpha + MotionMove + MotionMoveZ
  ↓
f_00066CB2()
  ↓
PartsLoad(nil) / GraphLoad(nil) 等资源卸载与状态清理
```

因此，`$chara_delete` 是**登记离场请求**；真正让角色移动、淡出并释放资源的是后续 `$chara_disp` 所触发的批处理刷新链。

## 2. 函数边界与参数偏移

### 2.1 函数边界

- 地址：`0x00060433–0x00060440`
- 指令数：很少，仅是转发包装器
- 拆分结果：[`f_00060433.lua`](Sakura_hcb_ir/Sakura/f_00060433.lua:1)
- 唯一被调函数：[`f_0005FE1E()`](Sakura_hcb_ir/Sakura/f_0005FE1E.lua:1)
- 调用者：共有 17 个函数直接调用它，跨越共通与主要剧情函数；调用总数为 508。

### 2.2 Lua-like 参数名存在整体偏移

表面函数头为：

```lua
function f_00060433(a0, a1)
```

但函数体实际读取的是 `a1`、`a2` 并原样转发：

```lua
f_0005FE1E(a1, a2)
```

这是本项目已确认的 Lua-like 导出器“形参名右移一位”问题。因此下文按**实际调用顺序**命名：

| 实际调用实参 | `f_00060433()` 函数体名 | 本报告名称 | 含义 |
|---|---|---|---|
| 第 1 个 | `a1` | `slot` | 待删除的立绘逻辑槽位编号 |
| 第 2 个 | `a2` | `exit_mode` | 离场位移模式；缺省为 `0` |

## 3. [`f_00060433()`](Sakura_hcb_ir/Sakura/f_00060433.lua:1) 本体：无条件转发

函数完整有效逻辑只有：

```lua
function CharDelete(slot, exit_mode)
    return f_0005FE1E(slot, exit_mode)
end
```

它本身：

- 不调用 [`MotionAlpha()`](../../syscall语义数据库/syscall含义详解/18_Motion.md:1)；
- 不调用 [`MotionMove()`](../../syscall语义数据库/syscall含义详解/18_Motion.md:1)；
- 不调用 [`PartsLoad()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:144)；
- 不调用 `GraphLoad(nil)`；
- 不等待动作结束。

所以不要把它直接理解为“已经完成立绘删除”的同步函数。它只是为了让上层 KS 宏简洁调用而存在的薄包装。

## 4. 下游核心：[`f_0005FE1E()`](Sakura_hcb_ir/Sakura/f_0005FE1E.lua:1)

### 4.1 第二参数缺省值

下游入口先执行：

```lua
if exit_mode == nil then
    exit_mode = 0
end
```

这说明：

```lua
f_00060433(slot, nil)
```

等价于：

```lua
f_00060433(slot, 0)
```

也就是说，KS 中绝大多数不写 `#param` 的调用，实际都使用 `exit_mode = 0`。

### 4.2 第一个参数如何映射到状态槽

[`f_0005FE1E()`](Sakura_hcb_ir/Sakura/f_0005FE1E.lua:16) 依次识别：

```text
slot = 1..19、21..24、0
```

每个有效 `slot` 都执行相同结构：

```lua
G[311 + logical_index] = 3    -- 对应槽位进入删除待处理状态
G[815 + logical_index] = nil  -- 清除该槽位的刷新抑制/特殊标志
G[599 + logical_index] = exit_mode  -- 仅在原始第二参数非 nil 时写入
flip corresponding G[359]..G[382] flag
```

其中实际映射并非简单的 `G[311 + slot]` 连续下标，因为 `slot=0` 放在最后、`slot=20` 缺席；但概念上是一张 24 组立绘槽位表。

例如：

| `slot` | 删除状态 | 离场模式缓存 | 配对状态 |
|---:|---|---|---|
| `1` | `G[311] = 3` | `G[599] = exit_mode` | 切换 `G[359]` |
| `2` | `G[312] = 3` | `G[600] = exit_mode` | 切换 `G[360]` |
| `3` | `G[313] = 3` | `G[601] = exit_mode` | 切换 `G[361]` |
| `4` | `G[314] = 3` | `G[602] = exit_mode` | 切换 `G[362]` |
| `…` | `…` | `…` | `…` |
| `24` | `G[333] = 3` | `G[621] = exit_mode` | 切换 `G[381]` |
| `0` | `G[334] = 3` | `G[622] = exit_mode` | 切换 `G[382]` |

`slot=20` 在函数中没有分支，因此不能假定它是有效的普通立绘编号。

### 4.3 `G[311]..G[334] = 3` 的含义

[`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:795) 在每个槽位的刷新逻辑中将状态 `3` 作为专门分支处理；[`f_00066CB2()`](Sakura_hcb_ir/Sakura/f_00066CB2.lua:1190) 随后专门检查各槽位是否等于 `3`，并清空：

- 角色/立绘状态；
- Parts 绑定信息；
- 当前离场模式缓存；
- 坐标、颜色、alpha 等相关缓存；
- Parts 与 Graph 资源。

因此 `3` 可以高可信理解为：

> **该立绘槽位已请求离场，等待本轮立绘批处理执行淡出/移动后回收。**

它不是“角色 ID=3”，而是每个逻辑槽位的状态值。

## 5. 第二参数：离场位移模式的直接证据

### 5.1 数据流

当 `exit_mode` 非 `nil` 时，删除函数将它保存到对应缓存，例如：

```lua
G[599] = exit_mode  -- slot 1
G[600] = exit_mode  -- slot 2
```

然后 [`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:795) 读取该缓存：

```lua
f_00068A8C(G[599], distance)
```

[`f_00068A8C()`](Sakura_hcb_ir/Sakura/f_00068A8C.lua:1) 并不处理 Parts 条目或资源，而是把输入模式翻译为三个运动偏移量：

```text
G[1170] = ΔX
G[1171] = ΔY
G[1172] = ΔZ
```

随后 [`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:803) 将这些偏移加到当前/目标坐标，再把结果交给：

- [`MotionMove()`](../../syscall语义数据库/syscall含义详解/18_Motion.md:1)
- [`MotionMoveZ()`](../../syscall语义数据库/syscall含义详解/18_Motion.md:1)

所以第二参数是运动方向/组合模式，而非资源或表情参数。

### 5.2 模式完整对照表

以下表直接来自 [`f_00068A8C()`](Sakura_hcb_ir/Sakura/f_00068A8C.lua:5) 的分支逻辑。设本次批处理传给它的距离为 `D`。

| `exit_mode` | `ΔX` | `ΔY` | `ΔZ` | 可解释的离场方向 |
|---:|---:|---:|---:|---|
| `0` | `0` | `0` | `0` | 默认：不附加位移，仅淡出/回收 |
| `1` | `+D` | `0` | `0` | 向 +X 离场 |
| `2` | `-D` | `0` | `0` | 向 -X 离场 |
| `3` | `0` | `+D` | `0` | 向 +Y 离场 |
| `4` | `0` | `-D` | `0` | 向 -Y 离场 |
| `5` | `+D` | `+D` | `0` | 向 +X,+Y 斜向离场 |
| `6` | `-D` | `+D` | `0` | 向 -X,+Y 斜向离场 |
| `7` | `+D` | `-D` | `0` | 向 +X,-Y 斜向离场 |
| `8` | `-D` | `-D` | `0` | 向 -X,-Y 斜向离场 |
| `9` | 未定义 | 未定义 | 未定义 | 不在 [`f_00068A8C()`](Sakura_hcb_ir/Sakura/f_00068A8C.lua:1) 的有效分支内；不建议使用 |
| `10` | `0` | `0` | `+150` | +Z 离场 |
| `11` | `0` | `0` | `-150` | -Z 离场 |
| `12` | `0` | `+D` | `+150` | +Y,+Z 离场 |
| `13` | `0` | `+D` | `-150` | +Y,-Z 离场 |
| `14` | `+D` | `0` | `+150` | +X,+Z 离场 |
| `15` | `+D` | `0` | `-150` | +X,-Z 离场 |
| `16` | `-D` | `0` | `+150` | -X,+Z 离场 |
| `17` | `-D` | `0` | `-150` | -X,-Z 离场 |

注意：`+X/-X`、`+Y/-Y` 是引擎坐标符号，不应在没有实机坐标朝向验证时直接机械命名为“右/左/上/下”。但从现有剧情文本可确认：`1/2` 是相反的一对水平离场模式。

### 5.3 `nil` 和 `0` 的实际区别

在最终运动效果上：

```text
nil → 下游归一化为 0 → 无额外位移
0   → 直接无额外位移
```

但缓存写入过程略有不同：

- `nil`：删除函数本身不写 `G[599]..G[622]`，因为原值为空；后续刷新路径把它解释为 `0`。
- `0`：删除函数明确把 `0` 写入对应缓存。

对正常脚本使用而言，两者均表示标准无位移删除；推荐沿用原作默认的 `nil`/省略 `#param`。

## 6. 与 `$chara_delete` 的 KS 对照

### 6.1 默认删除

原作最常见形式：

```ks
[macro name="$chara_delete" #cname="..."]
```

这对应：

```lua
f_00060433(slot, nil)
```

其后通常紧跟：

```ks
[macro name="$chara_disp" #time="..."]
```

例如同一文件中可见大量 `$chara_delete` 后再调用 `$chara_disp` 的序列，如 [`route_haru.ks`](../../reference/SakuraMoyu_NS/route_haru.ks:17533)。这与“删除先登记、显示宏负责真正刷新”的调用链一致。

### 6.2 `#param="2"`：反向 X 方向离场

原作实例：

```ks
[macro name="$chara_delete" #cname="..." #param="2"]
[macro name="$chara_disp" #time="600" #disp="250"]
```

可见于 [`route_haru.ks`](../../reference/SakuraMoyu_NS/route_haru.ks:9821)。

对应的底层效果是：

```text
exit_mode = 2
→ ΔX = -D
→ 在 $chara_disp 的批处理阶段，立绘淡出并沿 -X 方向移动
```

此处 `#disp="250"` 与 `$chara_disp` 的刷新参数共同决定本轮可见的移动幅度/时序；它不是 `$chara_delete` 第二参数本身的含义。

### 6.3 `#param="1"`：正向 X 方向离场

原作实例：

```ks
[macro name="$chara_delete" #cname="..." #param="1"]
[macro name="$chara_disp"]
```

可见于 [`route_haru.ks`](../../reference/SakuraMoyu_NS/route_haru.ks:29193)。

对应：

```text
exit_mode = 1
→ ΔX = +D
→ 立绘在后续刷新中淡出并沿 +X 方向移动
```

### 6.4 语义与剧情文本的交叉印证

在 HCB 反编译结果中，可以直接看到：


见 [`f_000A2981.lua`](Sakura_hcb_ir/Sakura/f_000A2981.lua:27932)。

以及：

## 7. 删除请求如何真正执行

### 7.1 `$chara_delete` 只设状态

[`f_0005FE1E()`](Sakura_hcb_ir/Sakura/f_0005FE1E.lua:21) 将目标槽位状态设为 `3`，并保存离场模式；但它没有任何 `Motion*` 或资源卸载 syscall。

因此单独调用：

```lua
f_00060433(slot, exit_mode)
```

通常只会登记状态，不能保证屏幕立即发生变化。

### 7.2 `$chara_disp` 对应刷新链

原作通常在删除请求后触发 `$chara_disp`。在 HCB 中，该阶段会走入：

```text
f_00060441(...)
  → f_00060795(...)
  → f_00066CB2()
```

[`f_00060441()`](Sakura_hcb_ir/Sakura/f_00060441.lua:5) 是薄封装，仅将后 3 个实际入参转交 [`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:1)，再调用 [`f_00066CB2()`](Sakura_hcb_ir/Sakura/f_00066CB2.lua:1) 收束。

### 7.3 批处理阶段

[`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:795) 对每个立绘槽位：

1. 读取该槽位的 `exit_mode` 缓存；
2. 调 [`f_00068A8C()`](Sakura_hcb_ir/Sakura/f_00068A8C.lua:1) 展开 ΔX/ΔY/ΔZ；
3. 根据状态 `G[311]..G[334]` 判断是否属于删除状态 `3`；
4. 对成对的图元执行 `MotionAlpha`，令 alpha 向 `0` 收束；
5. 对其执行 `MotionMove` / `MotionMoveZ`，将离场偏移叠加到目标坐标；
6. 设置批处理完成标志。

### 7.4 最终资源清理

[`f_00066CB2()`](Sakura_hcb_ir/Sakura/f_00066CB2.lua:1190) 对状态为 `3` 的槽位做最终收束：

- 清空槽位状态、位置与相关缓存；
- 清空 `G[599]..G[622]` 的离场模式缓存；
- 调用 [`PartsLoad(id, nil)`](../../syscall语义数据库/syscall含义详解/20_Parts.md:144) 卸载部件像素数据；
- 对相应对象进行 `GraphLoad(id, nil)`；
- 停止 alpha、位移、Z 等 motion；
- 恢复可复用的立绘槽位状态。

所以“删除”实际是一条异步演出/回收链，不是一次立即的 `PrimSetNull`。

## 8. 与立绘引入函数的共享数据区

[`f_00058B8C()`](Sakura_hcb_ir/Sakura/f_00058B8C.lua:12801) 在立绘引入/更新时，同样会为每个逻辑槽位把其第 7 个实际参数写入：

```text
G[599]..G[622]
```

这与删除函数写入相同的缓存区域。

随后 [`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:795) 统一把这组缓存传给 [`f_00068A8C()`](Sakura_hcb_ir/Sakura/f_00068A8C.lua:1)。因此：

> `G[599]..G[622]` 是“本轮立绘构图/运动方向模式”缓存，既可由立绘引入设置，也可由立绘删除覆盖。

在 `$chara_delete` 语境中，它专门表示离场方向；在 `$chara` 引入语境中，同一数值可能表达进场/布局的方向模式。不能脱离调用位置把它一概称为“删除方向”。

## 9. 推荐调用方式

### 9.1 标准无位移删除

```lua
f_00060433(slot, nil)
-- 后续必须触发原作的立绘刷新链
f_00060441(...)
```

KS 对应：

```ks
[macro name="$chara_delete" #cname="..."]
[macro name="$chara_disp"]
```

### 9.2 水平方向离场

```lua
f_00060433(slot, 1)  -- +X
f_00060433(slot, 2)  -- -X
```

KS 对应：

```ks
[macro name="$chara_delete" #cname="..." #param="1"]
[macro name="$chara_disp" ...]
```

或：

```ks
[macro name="$chara_delete" #cname="..." #param="2"]
[macro name="$chara_disp" ...]
```

### 9.3 其他模式

`3..8`、`10..17` 的底层方向组合已经确定，但本次未找到 Sakura 原作 `$chara_delete` 显式传入这些模式的案例。因此：

- 从函数实现上，它们是有效方向模式；
- 但尚未得到原作 `$chara_delete` 实战案例的视觉验证；
- 若用于新增脚本，建议先对单个可回收测试立绘进行实机验证。

## 11. 最终结论摘要

1. [`f_00060433()`](Sakura_hcb_ir/Sakura/f_00060433.lua:1) 是 `$chara_delete` 的底层薄包装，不直接删除资源。
2. 第一个参数是要删除的立绘逻辑槽位编号，不等于最终 prim ID。
3. 第二个参数是离场位移模式；`nil` 等效于 `0`，即无额外位移。
4. `1` 与 `2` 分别代表一对相反的水平离场方向：`+X` 和 `-X`。
