# [`f_000822AD()`](Sakura_hcb_ir/Sakura/f_000822AD.lua:1) 详细解析

## 1. 核心结论

[`f_000822AD()`](Sakura_hcb_ir/Sakura/f_000822AD.lua:1) 是 Sakura.hcb 中一个**特殊演出/场景图像状态分发入口**。

它自身非常短，主要完成三件事：

1. 对第 5 个真实参数做 `nil` 默认化；
2. 调用 [`f_00037F11()`](Sakura_hcb_ir/Sakura/f_00037F11.lua:1) 刷新一组场景/UI 辅助状态；
3. 将其余 4 个真实参数转发给 [`f_00081CDD()`](Sakura_hcb_ir/Sakura/f_00081CDD.lua:1)，由后者按照模式号选择具体演出分支。

语义化表示为：

```lua
function dispatch_scene_effect(refresh_arg, mode, value, duration_or_context, run_mode)
    if run_mode == nil then
        run_mode = nil
    end

    f_00037F11(0, nil)
    f_00081CDD(mode, value, duration_or_context, run_mode, nil)
end
```

但是，由于 HCB Lua-like 导出器存在参数名整体偏移，以上变量名只是语义化名称。严格的真实参数关系见第 4 节。

最准确的功能标签是：

> **在刷新场景/UI 状态后，按演出模式号分发并启动一组特殊图像/动画演出。**

它不是单纯的图片加载函数，也不是某一张 CG 的专用入口。真正的模式选择、参数缓存、线程启动和图像动画执行发生在 [`f_00081CDD()`](Sakura_hcb_ir/Sakura/f_00081CDD.lua:1) 与 [`f_0007B501()`](Sakura_hcb_ir/Sakura/f_0007B501.lua:1) 中。

## 3. 原始反编译代码

[`f_000822AD.lua`](Sakura_hcb_ir/Sakura/f_000822AD.lua:1) 的完整主体如下：

```lua
function f_000822AD(a0, a1, a2, a3, a4)
  local S0, S1, S2, S3, S4, S5, S6
  ::BB_000822AD:: -- block 0, succs=[2, 1]
  -- init_stack args=5 locals=0
  S0 = a5
  S1 = nil
  S0 = (S0 == S1)
  if __is_nil(S0) then goto BB_000822BC end
  ::BB_000822B9:: -- block 1, succs=[2]
  S0 = nil
  a5 = S0
  ::BB_000822BC:: -- block 2, succs=[]
  S0 = 0
  S1 = nil
  __ret = f_00037F11(S0, S1)
  S0 = a1
  S1 = a2
  S2 = a3
  S3 = a4
  S4 = a5
  __ret = f_00081CDD(S0, S1, S2, S3, S4)
  return
end
```

逐条解释：

| 顺序 | 指令/IR | 作用 |
|---:|---|---|
| 1 | `init_stack args=5 locals=0` | 建立 5 个真实入参、无显式局部变量的栈帧 |
| 2 | 读取 `a5` | 读取第 5 个真实参数；这是导出器偏移名称 |
| 3 | 与 `nil` 比较 | 判断第 5 个参数是否缺省 |
| 4 | 缺省时写回 `nil` | 将该参数显式规范化为 `nil` |
| 5 | `f_00037F11(0,nil)` | 刷新场景/UI 辅助状态 |
| 6 | `f_00081CDD(...)` | 进入按模式号分发的核心函数 |
| 7 | `return` | 无业务返回值 |

第 2 步的 `nil -> nil` 看似没有变化，但它具有明确的脚本语义：

> **确保传给下游的第五个参数为 nil，而不是保留其它类型或调用上下文中的非 nil 值。**

## 4. 参数编号勘误与真实参数映射

### 4.1 函数实际上有 5 个参数

函数序言为：

```text
init_stack args=5 locals=0
```

所以真实参数为 `P0..P4`。

导出器函数头显示：

```lua
function f_000822AD(a0, a1, a2, a3, a4)
```

但函数体读取 `a5`，这与项目已有的 Lua-like 参数编号整体右移问题一致。相关说明见 [`HCB Lua-like参数编号偏移错误说明.md`](HCB%20Lua-like参数编号偏移错误说明.md:1)。

正确映射如下：

| 真实参数 | 原始负栈槽 | 导出器旧名称 | 在本函数中的作用 |
|---|---:|---|---|
| `P0` | `-6` | `a1` | 传给 `f_00037F11` 的第一个参数；本函数固定改传 `0`，因此 P0 对下游无直接作用 |
| `P1` | `-5` | `a2` | 演出模式号，传给 `f_00081CDD` 第 1 参数 |
| `P2` | `-4` | `a3` | 模式相关数值，传给 `f_00081CDD` 第 2 参数 |
| `P3` | `-3` | `a4` | 演出时间/上下文参数，传给 `f_00081CDD` 第 3 参数 |
| `P4` | `-2` | `a5` | 执行模式/线程控制参数，`nil` 时保持为 nil，传给 `f_00081CDD` 第 4 参数 |

这里最容易误判的是 `P0`：虽然它是 `f_000822AD()` 的第一个真实入参，但本函数并没有把它传给 [`f_00037F11()`](Sakura_hcb_ir/Sakura/f_00037F11.lua:1)，而是固定压入：

```lua
f_00037F11(0, nil)
```

因此 `P0` 在当前函数体中属于**未使用参数**。它可能是为了保持调用约定统一，也可能是原脚本接口中保留的上下文参数。

## 5. 第一阶段：参数 `P4` 的 nil 规范化

函数首先处理第五个真实参数：

```lua
if P4 ~= nil then
    P4 = nil
end
```

从反编译控制流看，逻辑是：

```lua
S0 = P4
S1 = nil
S0 = (S0 == S1)
if __is_nil(S0) then
    P4 = nil
end
```

由于导出器条件跳转的表示方式容易把真假方向读反，这一段最可靠的事实是：

> 在进入 [`f_00081CDD()`](Sakura_hcb_ir/Sakura/f_00081CDD.lua:1) 前，第五个传递值最终被规范化为 `nil`。

因此当前函数调用下游时，形式上等价于：

```lua
f_00081CDD(P1, P2, P3, nil, nil)
```

这也是为什么绝大多数剧情调用即使在外层准备了 5 个值，进入 `f_00081CDD` 后，最后两个控制位仍表现为 nil/默认路径。

## 6. 第二阶段：调用 `f_00037F11(0,nil)`

函数固定执行：

```lua
f_00037F11(0, nil)
```

对应 [`f_000822AD.lua`](Sakura_hcb_ir/Sakura/f_000822AD.lua:13-15)。

[`f_00037F11()`](Sakura_hcb_ir/Sakura/f_00037F11.lua:1) 会：

1. 根据第二参数判断是否设置 `G[296]`；
2. 在特定值下调用 [`f_0004A5DE()`](Sakura_hcb_ir/Sakura/f_0004A5DE.lua:1)；
3. 最终调用 [`f_00037E76()`](Sakura_hcb_ir/Sakura/f_00037E76.lua:1)。

而 [`f_00037E76()`](Sakura_hcb_ir/Sakura/f_00037E76.lua:1) 会处理 prim `291`、`293` 的创建、透明度和销毁状态。

在 `f_000822AD()` 中固定传入 `(0,nil)`，说明这个前置动作并不是由调用者自由选择的，而是本入口的标准环境准备步骤。

因此它可以概括为：

> **进入特殊演出前，先将场景/UI 辅助图元和相关显示状态刷新到统一基线。**

这一步不负责选择具体演出模式，也不负责主演出图像的加载；它是进入 [`f_00081CDD()`](Sakura_hcb_ir/Sakura/f_00081CDD.lua:1) 前的固定前置准备。

## 7. 第三阶段：进入 `f_00081CDD()`

外层最终执行：

```lua
f_00081CDD(P1, P2, P3, P4, nil)
```

由于 `P4` 在外层已被规范化为 nil，通常可以进一步理解为：

```lua
f_00081CDD(mode, value, context, nil, nil)
```

[`f_00081CDD()`](Sakura_hcb_ir/Sakura/f_00081CDD.lua:1) 的控制流特点是：

- 前两个全局状态条件可能直接让出一帧并返回；
- 对 `mode` 进行连续比较；
- 模式号对应不同的全局槽；
- 将 `value` 写入该模式的状态槽；
- 将第三参数写入统一的 `G[1219]`；
- 根据第 4 参数是否等于 `-1`，选择后台线程还是直接执行 [`f_0007B501()`](Sakura_hcb_ir/Sakura/f_0007B501.lua:1)。

调用结构如下：

```text
f_000822AD
    -> f_00037F11(0,nil)
    -> f_00081CDD(mode,value,context,nil,nil)
        -> mode 分支
        -> G[1195..1218] 中某个槽 = value
        -> G[1219] = context
        -> ThreadStart(4, 505089) 或 f_0007B501()
```

## 8. `f_00081CDD()` 的模式分发

### 8.1 模式 0

当：

```text
P1 == 0
```

函数将 `P2` 写入：

```text
G[1218]
```

并将 `P3` 写入：

```text
G[1219]
```

随后启动或直接执行 [`f_0007B501()`](Sakura_hcb_ir/Sakura/f_0007B501.lua:1)。

### 8.2 模式 1

```text
P1 == 1
-> G[1195] = P2
-> G[1219] = P3
```

并且如果 `P5 == 19` 的条件成立，还会把 `P2` 同步写入 `G[1213]`。

### 8.3 模式 2 到 18

模式 `2..18` 基本使用连续状态槽：

| 模式号 | 状态槽 |
|---:|---|
| 0 | `G[1218]` |
| 1 | `G[1195]` |
| 2 | `G[1196]` |
| 3 | `G[1197]` |
| 4 | `G[1198]` |
| 5 | `G[1199]` |
| 6 | `G[1200]` |
| 7 | `G[1201]` |
| 8 | `G[1202]` |
| 9 | `G[1203]` |
| 10 | `G[1204]` |
| 11 | `G[1205]` |
| 12 | `G[1206]` |
| 13 | `G[1207]` |
| 14 | `G[1208]` |
| 15 | `G[1209]` |
| 16 | `G[1210]` |
| 17 | `G[1211]` |
| 18 | `G[1212]` |

每个分支的共同结构是：

```lua
G[mode_slot] = P2
G[1219] = P3
if P4 ~= -1 then
    ThreadStart(4, 505089)
else
    f_0007B501()
end
```

### 8.4 模式 19

模式 `19` 特殊之处在于直接使用：

```text
G[1213] = P2
G[1219] = P3
```

`G[1213]` 既可能保存模式 19 的数值，也会在其它模式的条件分支中被复用，因此它是一个共享的特殊演出状态槽。

### 8.5 模式 20

模式 `20` 使用：

```text
G[1214] = P2
G[1219] = P3
```

### 8.6 模式 21 到 24

后续模式使用连续槽：

| 模式号 | 状态槽 |
|---:|---|
| 21 | `G[1215]` |
| 22 | `G[1216]` |
| 23 | `G[1217]` |
| 24 | `G[1218]` |

模式 24 的分支位于 [`f_00081CDD()`](Sakura_hcb_ir/Sakura/f_00081CDD.lua:612-658) 附近。

### 8.7 模式表的整体意义

这些槽位不是 25 个完全独立的函数参数，而更像是：

```text
25 个特殊演出对象/状态项目的参数表
```

调用者通过 `mode` 选择当前要更新哪一项，通过 `value` 写入该项的数值，再由统一 worker [`f_0007B501()`](Sakura_hcb_ir/Sakura/f_0007B501.lua:1) 按这些全局状态批量处理。

因此 `P1` 的推荐名称是：

```text
special_effect_mode
```

或：

```text
scene_effect_slot
```

而不是直接称为“prim ID”。当前模式号 `1..24` 与最终图元 ID 并不相同。

## 9. 第 4 参数与线程执行方式

在 [`f_00081CDD()`](Sakura_hcb_ir/Sakura/f_00081CDD.lua:70-81) 等多个分支中都出现：

```lua
if P4 ~= -1 then
    ThreadStart(4, 505089)
else
    f_0007B501()
end
```

因此第 4 个传给 `f_00081CDD()` 的参数，也就是 `f_000822AD()` 的 `P3`，其核心作用是：

| 值 | 执行方式 |
|---:|---|
| `-1` | 直接在当前线程执行 `f_0007B501()` |
| 其它值 | 启动线程 4，入口地址 `505089` |

由于 `f_000822AD()` 的第 5 参数 `P4` 会被规范化成 nil，并作为 `f_00081CDD()` 的第 4 参数传递，因此通过 `f_000822AD()` 调用时通常会进入：

```text
P4 != -1
-> ThreadStart(4, 505089)
```

也就是说，`f_000822AD()` 默认倾向于让特殊演出在后台线程中执行。

这里要区分两个不同的“第 4 参数”：

- `f_000822AD()` 的第 4 个真实参数 `P3`：传给 `f_00081CDD()` 的第三位置，保存到 `G[1219]`；
- `f_00081CDD()` 的第 4 个真实参数：决定线程/当前线程执行方式；在 `f_000822AD()` 中通常来自被规范化后的 nil。

参数经过外层转发后发生了位置变化，不能只按外层序号理解。

## 10. `f_0007B501()` 的作用

[`f_0007B501()`](Sakura_hcb_ir/Sakura/f_0007B501.lua:1) 是真正的后台演出处理 worker。

其主要结构是：

1. 读取 `G[1195]..G[1213]` 等模式状态槽；
2. 将每个非零状态槽转换成对应的内部演出参数；
3. 读取 `G[623]..G[698]`、`G[503]..G[521]` 等参数/资源缓存；
4. 调用 [`f_0007BD9E()`](Sakura_hcb_ir/Sakura/f_0007BD9E.lua:1) 执行具体演出对象处理；
5. 处理完成后把相应状态槽清零。

例如模式 1 的路径：

```lua
if G[1195] ~= 0 then
    value = G[1195]
    f_0007BD9E(value, 100, G[623], G[624], G[625], G[626], ...)
    G[1195] = 0
end
```

模式 2、3、4、5 等也具有相同的模板，只是：

- 读取的状态槽不同；
- 使用的附加参数组不同；
- 传给 `f_0007BD9E()` 的默认对象编号不同。

因此 `f_000822AD()` 不是直接控制某个固定图元，而是向一个大型演出 worker 投递“模式 + 数值 + 上下文”。

## 11. `f_0007BD9E()` 的进一步分发

[`f_0007BD9E()`](Sakura_hcb_ir/Sakura/f_0007BD9E.lua:1) 会继续根据自身第 1 个参数选择多个具体 worker：

```text
mode 1 -> f_0007C5F1
mode 2 -> f_0007C7FE
mode 3 -> f_0007CBA6
mode 4 -> f_0007CDBB
mode 5 -> f_0007CFCE
...
```

它的调用形式会将：

- 数值参数；
- 位置参数；
- 颜色/透明度参数；
- `G[1219]`；
- 其它默认参数

组合起来传给具体演出 worker。

所以完整链条更准确地表示为：

```text
f_000822AD
  -> f_00081CDD
    -> f_0007B501
      -> f_0007BD9E
        -> f_0007C5F1 / f_0007C7FE / ...
          -> 具体 prim、Graph、Motion、Alpha、线程操作
```

这也是为什么 `f_000822AD()` 自身只有很少几条指令，但却能影响复杂的剧情演出。

## 12. 典型调用样本

### 12.1 默认/空参数调用

常见调用形式：

```lua
f_000822AD(nil, nil, nil, nil, nil)
```

其效果是：

```text
P0 = nil，当前函数不使用
P1 = nil，传入 f_00081CDD 后不匹配 0..24 的普通模式
P2 = nil
P3 = nil
P4 = nil -> 规范化为 nil
先执行 f_00037F11(0,nil)
再进入 f_00081CDD 的默认/非模式路径
```

是否会产生明显画面效果，取决于此前 `G[1195..1218]` 中是否已有状态值。

### 12.2 模式 1 示例

剧情中可见类似：

```lua
f_000822AD(0, 1, value, context, nil)
```

语义近似为：

```text
刷新通用场景/UI 状态
选择演出模式 1
将 value 写入 G[1195]
将 context 写入 G[1219]
启动线程 4 执行 f_0007B501
```

### 12.3 模式 2 示例

```lua
f_000822AD(0, 2, value, context, nil)
```

对应：

```text
G[1196] = value
G[1219] = context
ThreadStart(4, 505089)
```

### 12.4 模式 19 示例

模式 19 会将数值写入 `G[1213]`：

```lua
f_000822AD(0, 19, value, context, nil)
```

它可能触发与特殊演出状态、环境/场景对象或某个共享资源槽有关的 worker 路径。

### 12.5 大量剧情调用中的数值

调用方传入的 `P2` 经常是：

- 整数状态值；
- 图像/演出编号；
- `0`、`1`、`3`、`4`、`5` 等小模式值；
- 某些由剧情编译器生成的大型编号，如 `6000120`、`4000010` 等。

这些值不能直接全部命名为“图元编号”。它们首先进入模式状态槽，具体如何解释由模式对应的 worker 决定。

## 13. 与图片加载函数的区别

[`f_000822AD()`](Sakura_hcb_ir/Sakura/f_000822AD.lua:1) 与 BGimageLoading 类函数的分工不同：

| 类型 | 主要职责 |
|---|---|
| BGimageLoading | 选择背景资源名、加载 Graph、初始化 prim 位置/Z/RS/alpha |
| `f_000822AD` | 刷新场景状态，并投递特殊演出模式参数 |
| `f_00081CDD` | 按模式号把参数写入演出状态槽，并启动 worker |
| `f_0007B501` | 批量消费状态槽，组织具体演出对象 |
| `f_0007BD9E` | 继续按具体模式调用底层演出 worker |

因此不要将 `f_000822AD()` 直接称为“图片加载函数”。它更接近：

> **特殊场景演出对象的统一入口/参数分发器。**

图片资源可能在它的下游 worker 中被间接使用，但本函数自身没有 `GraphLoad`、`PrimSetSprt` 或 `PrimSetText` 等直接资源加载操作。

## 14. 与 `f_0005261B()` / `f_000526A3()` 的区别

| 函数 | 核心对象 | 主要作用 |
|---|---|---|
| [`f_0005261B()`](Sakura_hcb_ir/Sakura/f_0005261B.lua:1) | 全局 V3D 坐标 | 1 ms 快速 V3D motion/状态同步 |
| [`f_000526A3()`](Sakura_hcb_ir/Sakura/f_000526A3.lua:1) | 全局 V3D 坐标及辅助层 | 完整可配置镜头/V3D 演出 |
| [`f_000822AD()`](Sakura_hcb_ir/Sakura/f_000822AD.lua:1) | 特殊演出状态槽 | 分发模式化图像/动画演出 |

`f_000822AD()` 自身不调用 `V3DMotion()`，也不直接改变 V3D z。

## 15. 线程与同步注意事项

通过 [`f_000822AD()`](Sakura_hcb_ir/Sakura/f_000822AD.lua:1) 进入 [`f_00081CDD()`](Sakura_hcb_ir/Sakura/f_00081CDD.lua:1) 后，通常会启动线程 4：

```text
ThreadStart(4, 505089)
```

该线程执行 [`f_0007B501()`](Sakura_hcb_ir/Sakura/f_0007B501.lua:1) 的工作。调用方本身不会在 `f_000822AD()` 内部显式等待线程完成；线程生命周期由下游状态和其它线程管理逻辑负责。

因此，调用后立即执行下一条剧情指令时，可能出现：

```text
当前 function 已继续
后台演出仍在运行
```

这正是特殊演出可以与对白或其它画面动作并行存在的原因。

如果需要判断演出是否完成，应继续追踪：

- `G[1195..1218]` 对应状态槽是否清零；
- 具体 worker 的 `Motion*Test`；
- `ThreadExit`；
- 相关全局线程状态。

不能仅通过 `f_000822AD()` 的返回判断演出已经结束。

---

## 16. 状态槽生命周期

以模式 1 为例：

```text
调用 f_000822AD
    -> G[1195] = value
    -> 启动 f_0007B501
    -> f_0007B501 读取 G[1195]
    -> 调用 f_0007BD9E
    -> G[1195] = 0
```

其它模式同理：

```text
G[mode_slot] = value
    -> worker 消费
    -> mode_slot 清零
```

这说明这些槽位更像是：

> **一次性演出请求队列/状态寄存器。**

它们不一定保存长期配置；很多情况下，worker 读取后就清零。

`G[1219]` 则是多个模式共享的附加上下文槽，使用后是否清除需要结合具体 worker 继续判断。

## 17. 推荐参数命名

针对 [`f_000822AD()`](Sakura_hcb_ir/Sakura/f_000822AD.lua:1)，建议使用：

| 参数 | 推荐名称 | 说明 |
|---|---|---|
| `P0` | `unused_or_refresh_context` | 当前函数体固定不使用，不能强行命名 |
| `P1` | `effect_mode` | 传给 `f_00081CDD` 的模式号，负责选择状态槽 |
| `P2` | `effect_value` | 写入所选模式槽的数值 |
| `P3` | `effect_context` | 写入共享槽 `G[1219]` 的上下文/时间/附加参数 |
| `P4` | `worker_mode` | 进入本函数后通常被规范化为 nil，并影响下游线程/同步路径 |

需要强调：`P2` 和 `P3` 的最终业务意义依赖 `effect_mode`。同一个位置在不同模式下可能代表不同的演出参数，不能脱离模式号独立命名。

## 18. 对新剧情注入的建议

### 18.1 复用现有模式

如果目标是复现原作已有特殊演出，优先调用：

```lua
f_000822AD(0, effect_mode, effect_value, effect_context, nil)
```

其中第一个参数虽然当前函数不使用，但建议保留原作常见的 `0`，以保持调用形状一致。

### 18.2 不要直接改写状态槽而跳过入口

虽然可以直接写：

```lua
G[1195] = value
```

但这样会跳过：

```lua
f_00037F11(0,nil)
f_00081CDD(...)
```

可能导致：

- UI/辅助 prim 未刷新；
- worker 未启动；
- 线程状态不一致；
- 状态槽被其它演出覆盖。

### 18.3 不要将 `P2` 统一当作图元编号

模式 1、2、3 等分支只是把 `P2` 写入不同的槽位。具体 worker 可能将它解释为：

- 演出编号；
- 图片编号；
- 角色/对象状态；
- 资源索引；
- 某个动作模板参数。

注入前必须同时确认 `effect_mode` 和对应的 `f_0007BD9E()` 分支。

## 19. 最终结论

1. [`f_000822AD()`](Sakura_hcb_ir/Sakura/f_000822AD.lua:1) 是特殊演出/场景状态的统一入口。
2. 它有 5 个真实入参，但第一个真实参数在当前函数体中未使用。
3. 第五个真实参数会在进入下游前被规范化为 `nil`。
4. 函数固定先调用 [`f_00037F11(0,nil)`](Sakura_hcb_ir/Sakura/f_00037F11.lua:1)，刷新场景/UI 辅助状态。
5. 随后调用 [`f_00081CDD()`](Sakura_hcb_ir/Sakura/f_00081CDD.lua:1)。
6. `f_00081CDD` 的第一个参数是特殊演出模式号，当前可见模式范围为 `0..24`。
7. 模式号用于选择 `G[1195]..G[1218]` 中的某个状态槽。
8. 模式对应的数值被写入所选状态槽，共享上下文被写入 `G[1219]`。
9. 第 4 个传给 `f_00081CDD` 的控制参数为 `-1` 时直接执行 [`f_0007B501()`](Sakura_hcb_ir/Sakura/f_0007B501.lua:1)，其它情况通常启动 `ThreadStart(4,505089)`。
10. [`f_0007B501()`](Sakura_hcb_ir/Sakura/f_0007B501.lua:1) 消费这些状态槽，并进一步调用 [`f_0007BD9E()`](Sakura_hcb_ir/Sakura/f_0007BD9E.lua:1) 和多个具体演出 worker。
11. 本函数自身没有直接的图片加载、Motion 或 Graph syscall。
12. 它不是主舞台 V3D 镜头函数，也不是普通背景图片加载函数。
13. 它的真正作用是把剧情中的“模式 + 数值 + 上下文”转化为一次后台特殊演出请求。

最准确的一句话概括是：

> **`f_000822AD()` 先刷新通用场景/UI 状态，再把特殊演出模式及其参数交给 `f_00081CDD()`，由后者写入对应全局状态槽并启动 `f_0007B501()` 执行具体图像/动画演出。**
