# [`f_00037708()`](Sakura_hcb_ir/Sakura/f_00037708.lua:1) 逐条反汇编与作用解析

## 1. 结论摘要

[`f_00037708()`](Sakura_hcb_ir/Sakura/f_00037708.lua:1) 不是控制“居中文本布局”或“文本淡入/显示动画”的函数，而是 Sakura 脚本系统中的一个**可中断、逐帧轮询式等待函数**。

它的核心行为是：

1. 规范化两个入参；
2. 根据第二参数决定是否启动 Timer 0；
3. 进入循环，每帧检查：
   - 全局中断标志 `G[154]`；
   - Timer 0 是否达到指定时长；
   - 全局跳过标志 `G[1964]`；
   - 当前输入位图是否包含可跳过输入；
4. 若尚未满足退出条件，则调用 [`f_0003769F()`](Sakura_hcb_ir/Sakura/f_0003769F.lua:1) 让出当前帧；
5. 满足任一退出条件后返回。

因此，它更准确的名称应接近：

```lua
WaitUntilTimeoutOrInput(duration, mode)
```

而不是：

```lua
SetCenteredTextDisplayDuration(...)
```

## 2. 反编译与参数槽位说明

导出函数头为：

```lua
function f_00037708(a0, a1)
```

但函数体使用了 `a2`，这是当前 Lua-like 导出器存在的参数槽编号偏移问题。根据原始 [`Sakura.ir.json`](Sakura_hcb_ir/Sakura.ir.json:921173) 中的 `init_stack args=2 locals=2`、`push_stack -2`、`push_stack -3`，真实参数应按负栈槽解释：

| 真实参数 | 原始栈槽 | 导出中常见名称 | 作用 |
|---|---:|---|---|
| `p0` | `-3` | 导出中的 `a1` | 等待时长/Timer resolution；`nil` 时默认为 `1000` |
| `p1` | `-2` | 导出中的 `a2` | 等待模式；`nil` 时默认为 `0`，`-1` 为特殊可中断模式 |

此外，函数内部会复用参数槽作为临时变量：

- 导出中的 `a1` 先保存第二真实参数，随后被改写为 Timer 进度值；
- 导出中的 `a0` 在循环中被改写为 `InputGetState()` 返回值。

以下分析统一使用修正后的调用形式：

```lua
f_00037708(p0, p1)
```

## 3. 原始函数范围与控制流

函数起始地址是 `0x00037708`，主函数实际字节码范围为：

```text
0x00037708 - 0x000377E1
```

其中：

- `0x00037708 - 0x000377D6` 是函数主体；
- `0x000377E0` 为正常返回；
- `0x000377E1` 是相邻的冗余返回入口；
- `0x000377D6 -> 0x0003773C` 构成循环；
- `0x0003773C` 是循环头。

CFG 中循环头对应 [`Sakura.cfg.json`](../../03_data/cfg/Sakura.cfg.json:223791) 的 block 6，回边来自 block 21，说明这不是一次性的 `ThreadWait`，而是显式的逐帧轮询。

### 4.3 根据 `p1` 决定是否启动 Timer 0

| 地址 | 原始字节 | 指令 | 解析 |
|---|---|---|---|
| `0x00037726` | `10 FD` | `push_stack -3` | 读取 `p0`。 |
| `0x00037728` | `0C 01` | `push_i8 1` | 压入 `1`。 |
| `0x0003772A` | `19` | `neg` | 得到 `-1`。 |
| `0x0003772B` | `23` | `set_ne` | 判断 `p1 != -1`。注意这里按参数槽映射实际对应模式参数。 |
| `0x0003772C` | `07 3C 77 03 00` | `jz 0x0003773C` | 若为 `-1`，跳过 TimerSet，直接进入轮询。 |
| `0x00037731` | `0C 00` | `push_i8 0` | 压入 Timer ID `0`。 |
| `0x00037733` | `10 FD` | `push_stack -3` | 压入第二真实参数 `p1`，作为 Timer resolution。 |
| `0x00037735` | `03 8B 00` | `syscall TimerSet` | 执行 `TimerSet(0,p1)`。见 [`Timer` 语义说明](../syscalls/28_Timer.md:67)。 |
| `0x00037738` | `0C 00` | `push_i8 0` | 压入 `0`。 |
| `0x0003773A` | `16 01` | `pop_stack 1` | 将导出临时槽 `a1` 置为 `0`，供后续读取 Timer 进度。 |

从控制流可知：

```lua
if p1 ~= -1 then
    TimerSet(0, p1)
    temp = 0
end
```

这里有一个重要含义：

- `p1 == -1`：不启动新的 Timer 0；
- `p1 != -1`：启动/重置 Timer 0；
- `p1 == 0` 并不是“立即结束”，而是会尝试执行 `TimerSet(0,0)`。在当前参考实现中，resolution 需要为正数，因此原版脚本与实际引擎可能存在兼容性差异，或该模式依赖旧版 VM 的宽松处理。

| 地址 | 原始字节 | 指令 | 解析 |
|---|---|---|---|
| `0x0003773C` | `0C 00` | `push_i8 0` | 压入常量 `0`。 |
| `0x0003773E` | `07 E0 77 03 00` | `jz 0x000377E0` | 常量 `0` 被视为假，因此不跳转，继续执行循环体。 |

### 4.6 Timer 0 进度检查

| 地址 | 原始字节 | 指令 | 解析 |
|---|---|---|---|
| `0x00037758` | `10 FD` | `push_stack -3` | 读取模式参数。 |
| `0x0003775A` | `0C 01` | `push_i8 1` | 压入 `1`。 |
| `0x0003775C` | `19` | `neg` | 得到 `-1`。 |
| `0x0003775D` | `23` | `set_ne` | 判断模式是否不是 `-1`。 |
| `0x0003775E` | `07 7C 77 03 00` | `jz 0x0003777C` | 模式为 `-1` 时跳过 TimerGet。 |
| `0x00037763` | `0C 00` | `push_i8 0` | Timer ID `0`。 |
| `0x00037765` | `0C 64` | `push_i8 100` | TimerGet 的换算目标/默认值 `100`。 |
| `0x00037767` | `03 8A 00` | `syscall TimerGet` | 执行 `TimerGet(0,100)`。 |
| `0x0003776A` | `14` | `push_return` | 读取 syscall 返回值。 |
| `0x0003776B` | `16 01` | `pop_stack 1` | 临时保存 TimerGet 返回值。 |
| `0x0003776D` | `10 01` | `push_stack 1` | 取出 Timer 进度值。 |
| `0x0003776F` | `0C 64` | `push_i8 100` | 压入阈值 `100`。 |
| `0x00037771` | `25` | `set_ge` | 判断 Timer 进度是否 `>=100`。 |
| `0x00037772` | `07 7C 77 03 00` | `jz 0x0003777C` | 未达到阈值，继续后面的检查。 |
| `0x00037777` | `06 E0 77 03 00` | `jmp 0x000377E0` | 达到阈值，结束等待。 |

等价逻辑：

```lua
if p1 ~= -1 then
    progress = TimerGet(0, 100)
    if progress >= 100 then
        return
    end
end
```

根据 [`TimerGet`](../syscalls/28_Timer.md:114) 的参考实现，当 Timer 以 `resolution = p1` 启动时：

```text
TimerGet(0,100) = 100 * elapsed / p1
```

因此 `progress >= 100` 大致等价于：

```text
elapsed >= p1
```

也就是说，在 `p1 != -1` 的路径中，第二参数是 Timer 的目标时长/分辨率，单位最终表现为毫秒，但函数的实现方式是用百分比进度轮询，而不是直接调用 [`ThreadWait()`](../syscalls/27_Thread.md:229)。

### 4.9 `p1 == 0`：检查输入位 1、位 3、位 2

| 地址 | 原始字节 | 指令 | 解析 |
|---|---|---|---|
| `0x0003779C` | `10 00` | `push_stack 0` | 读取输入位图。 |
| `0x0003779E` | `0C 01` | `push_i8 1` | 掩码 `1`。 |
| `0x000377A0` | `1F` | `bit_test` | 判断 `(input & 1) != 0`。 |
| `0x000377A1` | `10 00` | `push_stack 0` | 再次读取输入位图。 |
| `0x000377A3` | `0C 03` | `push_i8 3` | 掩码 `3`。 |
| `0x000377A5` | `1F` | `bit_test` | 判断 `(input & 3) != 0`。 |
| `0x000377A6` | `21` | `or` | 合并前两个条件。 |
| `0x000377A7` | `10 00` | `push_stack 0` | 再次读取输入位图。 |
| `0x000377A9` | `0C 02` | `push_i8 2` | 掩码 `2`。 |
| `0x000377AB` | `1F` | `bit_test` | 判断 `(input & 2) != 0`。 |
| `0x000377AC` | `21` | `or` | 合并全部条件。 |
| `0x000377AD` | `07 B7 77 03 00` | `jz 0x000377B7` | 无输入则继续等待。 |
| `0x000377B2` | `06 E0 77 03 00` | `jmp 0x000377E0` | 有输入则提前结束。 |
| `0x000377B7` | `06 D6 77 03 00` | `jmp 0x000377D6` | 无输入，进入逐帧让出。 |

等价逻辑可化简为：

```lua
if p1 == 0 then
    if (input & 1) ~= 0
       or (input & 3) ~= 0
       or (input & 2) ~= 0 then
        return
    end
    goto yield_frame
end
```

其中 `(input & 3) != 0` 已经覆盖了 `(input & 1) != 0` 与 `(input & 2) != 0`，因此从纯布尔逻辑看，三个判断存在冗余：

```lua
(input & 3) ~= 0
```

即可覆盖这三个条件。原始脚本保留三次测试，可能来自编译器生成、旧版逻辑模板或不同位含义在原 VM 中的特殊处理。

需要保守说明的是：项目输入数据库确认这些值是输入位图，但各个位在 Sakura 原作中的具体按键映射仍需结合运行时输入配置进一步确认，不能仅凭 `1/2/3` 直接命名为某个确定按键。

| `0x000377BC` | `10 FE` | `push_stack -2` | 读取模式 `p1`。 |
| `0x000377BE` | `0C 01` | `push_i8 1` | 压入 `1`。 |
| `0x000377C0` | `19` | `neg` | 得到 `-1`。 |
| `0x000377C1` | `22` | `set_e` | 判断 `p1 == -1`。 |
| `0x000377C2` | `07 D6 77 03 00` | `jz 0x000377D6` | 若 `p1 != -1`，不满足特殊输入条件，直接让出一帧。 |
| `0x000377C7` | `10 00` | `push_stack 0` | 读取输入位图。 |
| `0x000377C9` | `0C 01` | `push_i8 1` | 掩码 `1`。 |

```lua
if p1 ~= 0 then

```

结合前面的分支，`p1 == -1` 是一种**不启动 Timer、但允许特定输入提前结束的无限/外部条件等待模式**。

### 4.11 逐帧让出并回到循环头

| 地址 | 原始字节 | 指令 | 解析 |
|---|---|---|---|
| `0x000377D6` | `02 9F 76 03 00` | `call 0x0003769F` | 调用 [`f_0003769F()`](Sakura_hcb_ir/Sakura/f_0003769F.lua:1)。 |
| `0x000377DB` | `06 3C 77 03 00` | `jmp 0x0003773C` | 回到循环头，下一帧重新检查。 |
| `0x000377E0` | `04` | `ret` | 返回。 |
| `0x000377E1` | `04` | `ret` | 相邻冗余返回。 |

现有分析已确认 [`f_0003769F()`](Sakura_hcb_ir/Sakura/f_0003769F.lua:1) 是 [`ThreadNext()`](../syscalls/27_Thread.md:188) 包装器。因此，该函数不是忙等，而是：

```lua
ThreadNext()
-- 下一帧继续执行
```

完整循环的结构是：

```lua
while true do
    if G[154] == 1 then
        G[154] = 0
        return
    end

    if mode ~= -1 and TimerGet(0, 100) >= 100 then
        return
    end

    if G[1964] == 1 then
        return
    end

    input = InputGetState()

    if mode == 0 then
        if (input & 3) ~= 0 then
            return
        end
    elseif mode == -1 and (input & 1) ~= 0 then
        return
    end

    ThreadNext()
end
```

## 5. 两个入参的准确含义

### 5.1 第一参数 `p0`

当 `p0 == nil` 时，函数把它归一化为 `1000`。但必须注意：在导出的主体中，真正执行 `TimerSet(0, p1)` 的地方使用的是模式参数槽，而不是简单的 `p0` 直传。因此，当前导出器的变量名不能直接用来推断“第一个参数就是 TimerSet 的第二参数”。

从实际调用与功能表现看：

- `p0` 是调用方传入的等待基准/时长类参数；
- `p0 == nil` 时使用默认值 `1000`；
- 但由于参数槽复用和导出编号偏移，原始字节层仍应以栈槽和调用点为准；
- 对 `f_00037708(500,nil)` 这类调用，调用方显然希望表达约 `500 ms` 的等待。

因此对 `p0` 的最稳妥命名是：

> **等待时长基准，通常按毫秒解释；在当前反编译结果中可能与 Timer resolution 槽发生导出名称错位。**

### 5.2 第二参数 `p1`

第二参数在调用点中有两种典型形式：

```lua
f_00037708(500, nil)
f_00037708(x, -1)
```

其行为区别明确：

| `p1` | 行为 |
|---|---|
| `nil` | 归一化为 `0`；进入普通可输入中断路径，并执行 Timer 初始化路径。 |
| `0` | 普通模式；检查输入位 `1/2/3`。 |
| `-1` | 特殊模式；跳过 Timer 初始化，检查 `G[154]`、`G[1964]` 和输入位 `1`。 |
| 其他非负值 | 通常进入 Timer 计时路径，并在 Timer 进度达到 `100` 时退出。 |

所以 `p1` 是：

> **等待模式/计时器控制参数，而不是文本布局参数。**

## 6. 与 [`f_000493AC(1,-1)`](Sakura_hcb_ir/Sakura/f_000493AC.lua:1) 的关系

在 Sakura 开场流程中，调用顺序是：

```lua
G[1276] = 1
f_000493AC(1, -1)
f_00037708(500, nil)
f_0004CEFD("世界がそっと、ため息をつく――", ...)
f_00037708(500, nil)
```

对应原始导出位置见 [`Sakura.lua`](../../04_outputs/lua_ir/Sakura.lua:315428)。

这组代码应拆成三个不同职责：

### 6.1 [`f_000493AC(1,-1)`](Sakura_hcb_ir/Sakura/f_000493AC.lua:1)：布局和 UI 状态切换

已有 [`f_000493AC()`](Sakura_hcb_ir/Sakura/f_000493AC.lua:1) 分析表明，它负责：

- 进入特殊/演出式文本布局；
- 重设文本缓冲；
- 调整文本窗口和相关 prim；
- 处理右侧 UI 与父组 `349`；
- 进行部分移动、alpha 和显示状态收束。

因此，“文本居中出现”的主要直接原因仍是 [`f_000493AC(1,-1)`](Sakura_hcb_ir/Sakura/f_000493AC.lua:1) 与 `G[1276] = 1` 所建立的特殊文本布局状态。

### 6.2 [`f_00037708(500,nil)`](Sakura_hcb_ir/Sakura/f_00037708.lua:1)：布局完成后的前置等待

这个调用发生在 [`f_000493AC()`](Sakura_hcb_ir/Sakura/f_000493AC.lua:1) 返回之后、[`f_0004CEFD()`](Sakura_hcb_ir/Sakura/f_0004CEFD.lua:1) 输出第一句文本之前：

```lua
f_000493AC(1,-1)
f_00037708(500,nil)
f_0004CEFD(text)
```

因此它的直接作用是：

> **在特殊文本布局切入后等待一段时间，随后才允许下一条文本输出。**

它可能让玩家感受到“居中文本缓慢进入”，但它本身没有调用 `PrimSetAlpha`、`MotionAlpha`、`TextSpeed`、`TextPrint` 或 `TextOutSize`，也没有对文本 prim 做动画。因此不能把它定性为“控制文本进入动画时长”。

### 6.3 后续的 [`f_00037708(500,nil)`](Sakura_hcb_ir/Sakura/f_00037708.lua:1)：句间节奏等待

每次 [`f_0004CEFD()`](Sakura_hcb_ir/Sakura/f_0004CEFD.lua:1) 输出一句后，脚本再次调用 `f_00037708(500,nil)`：

```lua
f_0004CEFD("世界がそっと、ため息をつく――")
f_00037708(500,nil)
f_0004CEFD("胸に。")
```

这说明它更像“句子之间的演出节奏/停顿”，而不是只服务于第一句的进入动画。

## 7. 对原猜想的判断

### 7.1 合理的部分

你的猜想中有一部分是合理的：

- 观察到 `f_000493AC(1,-1)` 后文本居中，说明该调用确实切换了特殊文本布局；
- 观察到画面不是瞬间推进，而是在约 `500 ms` 后才继续，说明紧随其后的 [`f_00037708(500,nil)`](Sakura_hcb_ir/Sakura/f_00037708.lua:1) 确实参与了可见演出时序；
- “接近 500 ms”与调用点的常量 `500` 高度对应，基本不是巧合。

### 7.2 不准确的部分

但“`f_00037708` 控制居中文本的显示耗时”这一表述不够准确，原因是：

1. 函数本身没有任何文本或图元操作；
2. 函数只调用 `TimerSet`、`TimerGet`、`InputGetState` 和 [`ThreadNext()`](../syscalls/27_Thread.md:188)；
3. 它的等待可以被 `G[154]`、`G[1964]` 或输入提前打断；
4. 相同函数被大量用于 dissolve、动画、菜单、V3D 同步和普通剧情停顿，显然不是居中文本专用；
5. 居中布局由 [`f_000493AC()`](Sakura_hcb_ir/Sakura/f_000493AC.lua:1) 及其调用的文本/prim/UI 操作建立。

### 7.3 最终修正后的结论

更准确的描述是：

> [`f_000493AC(1,-1)`](Sakura_hcb_ir/Sakura/f_000493AC.lua:1) 负责把正文切换到居中/演出式文本布局；紧随其后的 [`f_00037708(500,nil)`](Sakura_hcb_ir/Sakura/f_00037708.lua:1) 负责在该布局建立后进行一个约 `500 ms` 的、可被输入或全局状态中断的等待。因此，`f_00037708` 影响的是**文本演出的推进时刻和停顿时长**，而不是文本本身的淡入动画或显示速度。

如果运行时确实看到“文字逐渐淡入”，那么淡入效果应继续在 [`f_0004CEFD()`](Sakura_hcb_ir/Sakura/f_0004CEFD.lua:1) 内部、其下游文本显示函数或此前 [`f_000493AC()`](Sakura_hcb_ir/Sakura/f_000493AC.lua:1) 启动的 prim 动画中寻找；不能将该视觉效果归因于 [`f_00037708()`](Sakura_hcb_ir/Sakura/f_00037708.lua:1) 的等待循环本身。

## 8. 最终伪代码

考虑到当前导出器的参数槽命名存在偏移，下面给出按实际行为归纳的伪代码：

```lua
function f_00037708(p0, p1)
    if p1 == nil then
        p1 = 0
    end

    if p0 == nil then
        p0 = 1000
    end

    -- 当模式允许计时器时，启动 Timer 0
    if p1 ~= -1 then
        TimerSet(0, p1)
    end

    while true do
        if G[154] == 1 then
            G[154] = 0
            return
        end

        if p1 ~= -1 and TimerGet(0, 100) >= 100 then
            return
        end

        if G[1964] == 1 then
            return
        end

        local input = InputGetState()

        if p1 == 0 then
            if (input & 1) ~= 0
                or (input & 3) ~= 0
                or (input & 2) ~= 0 then
                return
            end
        elseif p1 == -1 then
            if (input & 1) ~= 0 then
                return
            end
        end

        f_0003769F() -- ThreadNext()
    end
end
```

其中 `p0/p1` 与当前 Lua-like 导出中的 `a1/a2` 存在槽位偏移，实际重建 HCB 时必须以原始 `push_stack` 索引为准。
