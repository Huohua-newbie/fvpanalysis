# [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 颜色参数写入与立绘颜色应用链分析

## 1. 结论先说

[`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 的本质不是直接调用 [`GraphRGB()`](../../syscall语义数据库/syscall含义详解/10_Graph.md:1) 或 [`PartsRGB()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:319)，而是：

> **按照“立绘/部件槽位编号”把一组三通道颜色参数写入全局颜色缓存，供后续的立绘批处理函数 [`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:1) 读取，再实际应用到 Graph 和 Parts。**

因此，用户观察到它“可以控制立绘颜色”是正确的，但需要补充两个边界：

1. 该函数本身只写缓存，不直接刷新画面。
2. 它不只服务立绘，也服务背景过渡层等其他使用同一套颜色模板的对象；实际对象由后续消费者决定。

关于“能否仅依靠此函数即时改变当前立绘颜色”，本次对 [`Sakura.hcb`](Sakura.hcb:1) 的原作调用得到保守结论：

> **原作没有提供“只调用 [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 即时刷新已经显示的立绘颜色”的实证案例。因此按原作行为保守判断：不应把它当作独立的即时变色接口。**

如果允许补充调用负责刷新立绘的 [`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:1)，则可以实现“写入颜色缓存后刷新当前立绘”的效果；但这已经不是仅依靠 [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 了。

## 2. 函数边界与反编译参数偏移

### 2.1 函数边界

- 函数起点：`0x00069F71`
- 函数终点：`0x0006A418` 附近
- 前一个相邻函数：[`f_00069F3A()`](Sakura_hcb_ir/Sakura/f_00069F3A.lua:1)；后继函数：[`f_0006A419()`](Sakura_hcb_ir/Sakura/f_0006A419.lua:1)
- 反编译拆分文件：[`f_00069F71.lua`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1)
- 合并 IR 文件：[`Sakura.lua`](Sakura.lua:210349)

### 2.2 参数编号必须按真实 VM 槽位理解

拆分文件表面上写成：

```lua
function f_00069F71(a0, a1, a2, a3)
```

但函数体实际读取的是 `a1`、`a2`、`a3`、`a4`。这与项目中已经记录的反编译器参数整体偏移问题一致，不能直接按照函数头的名字解释。

本报告统一使用更可靠的脚本层参数命名：

| 实际调用位置 | 反编译函数体中的变量 | 本报告名称 | 作用 |
|---|---|---|---|
| 第 1 个实参 | `a1` | `selector` | 颜色模板/立绘槽位选择器 |
| 第 2 个实参 | `a2` | `r` | 颜色第 1 通道，通常按 R 理解 |
| 第 3 个实参 | `a3` | `g` | 颜色第 2 通道，通常按 G 理解 |
| 第 4 个实参 | `a4` | `b` | 颜色第 3 通道，通常按 B 理解 |

这里的 `r/g/b` 是颜色色调参数，不是 [`ColorSet()`](../../syscall语义数据库/syscall含义详解/02_Color.md:44) 的完整 RGBA 调色板写入参数。后续 [`GraphRGB()`](../../syscall语义数据库/syscall含义详解/10_Graph.md:1) 与 [`PartsRGB()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:319) 都只接收这三个通道参数。

### 2.3 直接证据

例如原作中的调用形态：

```lua
f_00069F71(2, 5, 5, 5)
f_00069F71(3, 5, 5, 5)
f_00069F71(4, 5, 5, 5)
```

可见第 1 个实参在变化，而后三个参数保持为颜色值 `5, 5, 5`。这些调用可在大型剧情函数中直接看到，例如 [`f_000A2981.lua`](Sakura_hcb_ir/Sakura/f_000A2981.lua:11518) 和 [`f_00171AE0.lua`](Sakura_hcb_ir/Sakura/f_00171AE0.lua:16385)。

## 3. 函数整体控制流

函数可以概括为以下伪代码：

```lua
function f_00069F71(selector, r, g, b)
    -- 场景/系统状态可能强制改写 r
    if G[1989] ~= 1 and r ~= -10 then
        r = -2
    end

    if G[1255] == 1 and r ~= -10 then
        r = -2
    end

    -- 默认颜色
    if r == nil then r = 100 end
    if g == nil then g = 100 end
    if b == nil then b = 100 end

    -- 特殊值 -10：替换为固定颜色 15,20,25
    if r == -10 then
        r, g, b = 15, 20, 25
    end

    if selector == -1 then
        -- 将颜色写入一组或多组预设缓存
        -- 某些槽位固定写 100,100,100
        -- 其他槽位写入 r,g,b
    else
        -- selector = 0..19、21..24 时，写入对应三元组缓存
    end
end
```

需要特别注意：

- [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 不执行任何 syscall。
- 它没有调用 [`GraphRGB()`](../../syscall语义数据库/syscall含义详解/10_Graph.md:1)。
- 它没有调用 [`PartsRGB()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:319)。
- 它的所有实质操作都是写入 `G[743]..G[814]` 以及广播路径中的 `G[1239]..G[1241]`。

## 4. 前置状态与颜色参数归一化

### 4.1 `G[1989]` 与 `G[1255]` 会强制改写颜色参数

函数入口先检查：

```lua
G[1989] ~= 1 and r ~= -10
```

如果条件成立，就把 `r` 改成 `-2`。之后又检查：

```lua
G[1255] == 1 and r ~= -10
```

如果条件成立，同样把 `r` 改成 `-2`。

这说明第 2 个实参虽然通常可作为颜色第 1 通道，但并不是在任何运行状态下都能自由控制。特定全局模式下，函数会把它强制归一化为特殊值 `-2`。

结合背景切换函数的既有分析，`G[1255]` 是场景切换/过渡模式标记；[`f_00016F8E()`](Sakura_hcb_ir/Sakura/f_00016F8E.lua:16) 在背景清场时会调用 [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1)，并设置过渡相关状态。因此，函数的颜色参数与场景过渡系统存在共用关系。

### 4.2 `nil` 默认值

函数把颜色三个通道分别归一化为：

| 实参 | `nil` 时的默认值 |
|---|---:|
| `r` | `100` |
| `g` | `100` |
| `b` | `100` |

所以：

```lua
f_00069F71(selector, nil, nil, nil)
```

在没有被状态逻辑改写的前提下，等价于为目标缓存写入：

```text
100, 100, 100
```

这与 Sakura 的普通立绘颜色基准一致：`100,100,100` 可以理解为“不偏色”的中性基准，而不是 8 位颜色空间中常见的 `255,255,255`。

### 4.3 `r == -10` 的特殊路径

当第 2 个实参等于 `-10` 时，函数将三个通道改写为：

```text
r = 15
g = 20
b = 25
```

这是一组固定的深色调参数。它不是“通用负值颜色模式”，而是一个明确的特殊预设。

不过要注意：在入口的两个全局状态检查中，`r == -10` 会阻止被强制改写成 `-2`，说明 `-10` 是函数有意保留的特殊颜色请求。

## 5. 第 1 个实参 `selector` 的含义

### 5.1 `selector == -1`：广播/批量模板路径

当第 1 个实参为 `-1` 时，函数不选择单个三元组，而是进入广播路径，连续写入多组全局缓存。

原作中典型调用为：

```lua
f_00069F71(-1, -3, nil, nil)
f_00069F71(-1, -4, nil, nil)
```

它们出现在背景导入函数中，例如 [`f_0001063E.lua`](Sakura_hcb_ir/Sakura/f_0001063E.lua:116) 和 [`f_000107EC.lua`](Sakura_hcb_ir/Sakura/f_000107EC.lua:128) 一类的场景背景切换函数。

广播路径的作用不是“给编号为 -1 的立绘上色”，而是：

> **为整套立绘/部件/过渡模板预先准备多组颜色缓存。**

### 5.2 `selector == 0..19、21..24`：单组缓存路径

当第 1 个实参不是 `-1` 时，函数依次判断：

```text
0, 1, 2, ..., 19, 21, 22, 23, 24
```

各选择值对应一个连续的全局槽位三元组。

| `selector` | 颜色缓存 |
|---:|---|
| `0` | `G[812]..G[814]` |
| `1` | `G[743]..G[745]` |
| `2` | `G[746]..G[748]` |
| `3` | `G[749]..G[751]` |
| `4` | `G[752]..G[754]` |
| `5` | `G[755]..G[757]` |
| `6` | `G[758]..G[760]` |
| `7` | `G[761]..G[763]` |
| `8` | `G[764]..G[766]` |
| `9` | `G[767]..G[769]` |
| `10` | `G[770]..G[772]` |
| `11` | `G[773]..G[775]` |
| `12` | `G[776]..G[778]` |
| `13` | `G[779]..G[781]` |
| `14` | `G[782]..G[784]` |
| `15` | `G[785]..G[787]` |
| `16` | `G[788]..G[790]` |
| `17` | `G[791]..G[793]` |
| `18` | `G[794]..G[796]` |
| `19` | `G[797]..G[799]` |
| `21` | `G[800]..G[802]` |
| `22` | `G[803]..G[805]` |
| `23` | `G[806]..G[808]` |
| `24` | `G[809]..G[811]` |

例如：

```lua
f_00069F71(2, 5, 5, 5)
```

会执行：

```lua
G[746] = 5
G[747] = 5
G[748] = 5
```

再例如：

```lua
f_00069F71(24, 80, 90, 100)
```

会执行：

```lua
G[809] = 80
G[810] = 90
G[811] = 100
```

### 5.3 `selector == 20` 的异常

函数中没有发现 `selector == 20` 的分支。已出现的序列是：

```text
0..19、21..24
```

因此不能简单把它解释成完整的 `0..24` 五位槽位表。`20` 可能是：

- 被保留给其他逻辑；
- 在该作品版本中没有对应立绘槽；
- 由其他函数使用了不同的缓存位置；
- 或者是原始脚本设计中的空缺编号。

当前不建议人为补上 `20` 的映射。

### 5.4 未匹配选择值

如果 `selector` 不是 `-1`，也不属于上述有效分支，函数不会写入任何单组颜色缓存，然后直接返回。

因此以下调用不能按“任意立绘编号”理解：

```lua
f_00069F71(20, r, g, b)
f_00069F71(25, r, g, b)
f_00069F71(-2, r, g, b)
```

至少从该函数本体看，它们没有对应的有效写入分支。

## 6. 广播路径的具体写入规律

当 `selector == -1` 时，函数从 `G[743]` 开始连续写入多个缓存组，但并不是简单地把同一颜色复制到全部槽位。

根据 [`f_00069F71.lua`](Sakura_hcb_ir/Sakura/f_00069F71.lua:448) 之后的赋值序列，可以整理为：

| 缓存组 | 广播写入值 |
|---|---|
| `G[743]..G[745]` | 固定 `100,100,100` |
| `G[746]..G[754]` | 写入 `r,g,b` |
| `G[755]..G[757]` | 固定 `100,100,100` |
| `G[758]..G[784]` | 写入 `r,g,b` |
| `G[785]..G[811]` | 由后续广播代码继续按模板写入；整体上属于批量初始化区域 |
| `G[812]..G[814]` | 写入 `r,g,b` |
| `G[1239]..G[1241]` | 写入 `r,g,b` |

这里最重要的现象是：广播路径中存在固定中性颜色组 `100,100,100`。所以 `selector == -1` 不是一个简单的“把颜色应用到所有立绘”命令，而是：

> **根据当前场景/过渡模板，对一批槽位进行带有例外项的批量初始化。**

这也是为什么它在背景切换代码中出现时，不能直接据此断言它就是“背景图颜色函数”。它只是写入共享的颜色模板区，之后由不同消费者选择其中的组使用。

## 7. 颜色缓存的真正消费者：[`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:1)

### 7.1 每个颜色组都会被同时用于 Graph 与 Parts

[`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:1) 的立绘批处理代码以如下结构反复出现：

```lua
prim_id = G[945] - 99
GraphRGB(prim_id, G[743], G[744], G[745])
PartsRGB(G[945] - 99, G[743], G[744], G[745])
```

第二个立绘槽位对应：

```lua
GraphRGB(G[947] - 99, G[746], G[747], G[748])
PartsRGB(G[947] - 99, G[746], G[747], G[748])
```

这组证据直接说明：

- `G[743]..G[745]` 是某一组对象的颜色缓存；
- `G[746]..G[748]` 是下一组对象的颜色缓存；
- 每一组缓存会同时送入 [`GraphRGB()`](../../syscall语义数据库/syscall含义详解/10_Graph.md:1) 与 [`PartsRGB()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:319)；
- 对象编号不是直接等于 `selector`，而是由 `G[945]`、`G[947]` 等运行时槽位减去 `99` 得到。

### 7.2 `G[945]..G[994]` 才是运行时对象编号映射

[`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:4006) 与 [`f_00066CB2()`](Sakura_hcb_ir/Sakura/f_00066CB2.lua:22) 都使用：

```text
G[945], G[947], G[949], ... , G[994]
```

这些槽位在立绘系统初始化时保存实际 Graph/Parts 对象编号。初始化代码会对它们执行：

- [`PrimSetNull()`](../../syscall语义数据库/syscall含义详解/21_Prim.md:1)
- [`PartsLoad()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:144)
- [`GraphLoad()`](../../syscall语义数据库/syscall含义详解/10_Graph.md:1)
- 后续 [`GraphRGB()`](../../syscall语义数据库/syscall含义详解/10_Graph.md:1)
- 后续 [`PartsRGB()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:319)

因此需要区分两套编号：

| 编号体系 | 作用 |
|---|---|
| `selector = 0..24` | 选择 [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 内的颜色缓存组 |
| `G[945]..G[994]` | 运行时保存具体立绘 Graph/Parts 对象编号 |
| `G[743]..G[814]` | 保存颜色三元组缓存 |

不能直接把 `selector` 等同于最终的 prim ID。

### 7.3 `f_00060795()` 还会启动立绘运动

在颜色应用之后，[`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:1) 还会根据状态执行：

- [`MotionAlpha()`](../../syscall语义数据库/syscall含义详解/18_Motion.md:1)
- [`MotionMove()`](../../syscall语义数据库/syscall含义详解/18_Motion.md:1)
- [`MotionMoveZ()`](../../syscall语义数据库/syscall含义详解/18_Motion.md:1)
- [`PartsMotion()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:180)

所以它不是单纯的“刷新颜色”函数，而是立绘批量更新/运动控制器。颜色刷新只是其中一个固定阶段。

## 8. 与 [`f_00058B8C()`](Sakura_hcb_ir/Sakura/f_00058B8C.lua:1) 立绘引入流程的关系

现有立绘引入分析已经确认，[`f_00058B8C()`](Sakura_hcb_ir/Sakura/f_00058B8C.lua:1) 负责：

1. 根据角色、姿态、服装等参数拼接立绘资源名；
2. 使用 [`PartsLoad()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:144) 装载部件资源；
3. 使用 [`PartsAssign()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:111) 绑定 Parts 与 prim；
4. 使用 [`PartsSelect()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:352) 选择细分表情/部件帧；
5. 设置立绘的构图、位置、Z、缩放和透明度相关状态。

其典型核心片段为：

```lua
PartsAssign(parts_id, prim_id)
PartsSelect(parts_id, expression_id)
```

对应代码可见于 [`f_00058B8C.lua`](Sakura_hcb_ir/Sakura/f_00058B8C.lua:9953)。

这说明立绘显示对象需要先经过资源加载、Parts 绑定和帧选择，之后 [`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:4022) 才能根据运行时对象编号执行颜色应用。

因此，用户观察到的“颜色函数前面必然跟着立绘调用”从系统结构上是合理的：

> **颜色缓存可以提前写入，但要让它影响画面，必须存在已经登记好的 Graph/Parts 对象，并且必须经过后续批处理刷新。**

## 9. 函数上下相邻的其他函数

### 9.1 [`f_00069F3A()`](Sakura_hcb_ir/Sakura/f_00069F3A.lua:1)：Parts motion 轮询器

该函数没有颜色逻辑，作用是：

```lua
for parts_id = 100, 138 do
    while PartsMotionTest(parts_id) == true do
        ThreadNext()
    end
end
```

它负责等待一批 Parts motion 完成。因此它与颜色函数的关系属于“立绘部件演出系统相邻”，而不是同一颜色功能族。

### 9.2 [`f_0006A419()`](Sakura_hcb_ir/Sakura/f_0006A419.lua:1)：全局槽写入器

该函数只有一个有效操作：

```lua
G[12] = 参数
```

它不涉及 Graph、Parts、颜色或 motion。它只是地址上紧邻的基础函数，不属于 [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 的同功能组。

### 9.3 真正的功能近邻：[`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:1)

虽然地址上并不紧邻，但从调用关系和数据流看，[`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:1) 才是最重要的功能近邻：

```text
f_00069F71(selector, r, g, b)
        ↓
写入 G[743]..G[814]
        ↓
f_00060795(...)
        ↓
GraphRGB(...) + PartsRGB(...)
        ↓
MotionAlpha / MotionMove / PartsMotion
```

另一个封装入口是 [`f_00060441()`](Sakura_hcb_ir/Sakura/f_00060441.lua:1)：

```lua
f_00060441(...) -> f_00060795(...) -> f_00066CB2()
```

[`f_00066CB2()`](Sakura_hcb_ir/Sakura/f_00066CB2.lua:1) 会检查多个立绘对象的 alpha motion，并在必要时重建或清理 Parts/Graph 状态。因此原作常见的实际工作流是：

```text
颜色缓存设置
→ 立绘批量刷新/运动
→ alpha 状态检查与部件状态收束
```

## 10. 原作实际调用类型

### 10.1 背景切换调用：`(-1, -3/-4, nil, nil)`

背景导入函数中常见：

```lua
f_00069F71(-1, -3, nil, nil)
f_00069F71(-1, -4, nil, nil)
```

这些调用的上下文是：

1. 选择背景资源名并写入 `G[63]`；
2. 在特定差分背景下调用 [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1)；
3. 随后调用背景层加载函数 [`f_0005074C()`](Sakura_hcb_ir/Sakura/f_0005074C.lua:1) 或 [`f_00050859()`](Sakura_hcb_ir/Sakura/f_00050859.lua:1)；
4. 背景层函数内部对背景 prim 执行 [`GraphRGB()`](../../syscall语义数据库/syscall含义详解/10_Graph.md:1)。

所以这些调用证明：

- [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 的颜色缓存确实可被背景过渡系统使用；
- 但它本身并没有直接对背景图执行颜色操作；
- 背景图是否使用该颜色，取决于下游的背景/过渡函数如何读取缓存。

### 10.2 立绘/演出调用：`(2/3/4/8..., 5,5,5)`

剧情函数中出现大量类似：

```lua
f_00069F71(2, 5, 5, 5)
f_00069F71(3, 5, 5, 5)
f_00069F71(4, 5, 5, 5)
```

或者：

```lua
f_00069F71(8, 5, 5, 5)
f_00069F71(13, 5, 5, 5)
```

这些调用通常不是孤立的颜色命令，而是嵌在一组演出初始化操作中，之后紧跟：

```lua
f_00060441(...)
```

例如 [`f_000A2981.lua`](Sakura_hcb_ir/Sakura/f_000A2981.lua:11518) 中就是连续设置多个颜色模板后调用 [`f_00060441()`](Sakura_hcb_ir/Sakura/f_00060441.lua:1)。这说明颜色函数在原作中的角色更接近：

> **先为若干立绘槽位写入本次演出的色调参数，再交给统一立绘运动刷新器一次性应用。**

### 10.3 原作调用中没有发现的形式

本次检查没有发现以下可直接证明的原作模式：

```lua
-- 已有立绘保持不变
f_00069F71(2, 0, 0, 0)
-- 立即完成颜色刷新
```

也没有发现：

```lua
f_00069F71(selector, r, g, b)
-- 不调用 f_00060795 / f_00060441
-- 但当前画面已经发生颜色变化
```

因此不能根据函数本体的写缓存行为，反推出原作支持这种独立用法。

## 11. “即时改变立绘颜色”问题的最终判断

### 11.1 仅调用 [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1)：不应判断为可行

原因有三层：

1. 函数本体只有全局槽写入，没有 [`GraphRGB()`](../../syscall语义数据库/syscall含义详解/10_Graph.md:1) 或 [`PartsRGB()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:319)。
2. 颜色缓存真正被读取的位置在 [`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:4022) 等下游函数中。
3. 原作没有只调用 [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 就让现有立绘颜色改变的案例。

所以针对用户提出的“仅依靠此函数进行即时立绘颜色变换”，结论是：

> **不行，至少原作没有证据支持。**

### 11.2 写缓存后补充刷新函数：技术上存在可能

如果新增脚本允许调用原作内部函数，那么更合理的实验链是：

```lua
f_00069F71(selector, r, g, b)
f_00060795(...)
```

或者通过原作的二级封装：

```lua
f_00069F71(selector, r, g, b)
f_00060441(...)
```

但这需要满足：

- `selector` 对应的缓存组确实与目标立绘对象对应；
- 目标立绘已经通过 [`f_00058B8C()`](Sakura_hcb_ir/Sakura/f_00058B8C.lua:1) 或其他路径完成 Graph/Parts 注册；
- [`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:1) 的状态门控允许进入对应槽位分支；
- 不被后续的立绘重建、表情选择或场景切换覆盖。

因此这属于“颜色缓存 + 批量刷新”的组合用法，而不是 [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 的单函数即时变色能力。

### 11.3 更直接的替代方向

如果目标是对已经显示的单个立绘进行即时色调调整，从 syscall 语义看，更直接的接口是：

```lua
GraphRGB(prim_id, r, g, b)
PartsRGB(parts_id, r, g, b)
```

但在 Sakura 原作的立绘架构中，一个角色通常同时涉及 Graph 与 Parts 两层，所以只调用其中一个接口可能造成：

- Graph 层颜色改变而 Parts 层没有改变；
- Parts 纹理改变但最终 Graph 显示未同步；
- 后续批处理刷新时被缓存值覆盖。

因此原作选择 [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 统一保存颜色，再由 [`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:1) 同时调用 [`GraphRGB()`](../../syscall语义数据库/syscall含义详解/10_Graph.md:1) 和 [`PartsRGB()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:319)，从架构上是有原因的。

## 12. 推荐的调用说明

### 12.1 单组颜色缓存设置

在确认目标槽位后，可以使用：

```lua
f_00069F71(selector, r, g, b)
```

其中：

- `selector`：`0..19`、`21..24` 中的一个有效选择值；
- `r/g/b`：Sakura 立绘色调参数，通常以 `100` 为中性基准；
- `nil` 通道会默认成 `100`；
- `r == -10` 会进入固定 `15,20,25` 预设；
- 未知 `selector` 不会产生有效的单组写入。

### 12.2 背景/全局模板设置

```lua
f_00069F71(-1, preset, g, b)
```

其中 `-1` 表示广播模板路径，而不是普通立绘槽位。该路径会写入多组缓存，并对部分组固定使用 `100,100,100`。

### 12.3 若目标是已显示立绘的颜色改变

不能只停在：

```lua
f_00069F71(selector, r, g, b)
```

至少还需要研究并调用合适的刷新链：

```lua
f_00069F71(selector, r, g, b)
f_00060795(...)
```

或：

```lua
f_00069F71(selector, r, g, b)
f_00060441(...)
```

具体参数不能从 [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 单独推出，必须结合目标立绘当前的 `G[311]..G[334]` 状态、`G[945]..G[994]` 对象映射和 [`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:1) 的门控条件继续分析。

## 13. 最终结论摘要

| 问题 | 结论 |
|---|---|
| [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 是否与立绘颜色有关 | 是，高可信 |
| 是否只服务立绘 | 否，也参与背景/过渡等共享颜色模板 |
| 是否直接调用 [`GraphRGB()`](../../syscall语义数据库/syscall含义详解/10_Graph.md:1) | 否 |
| 是否直接调用 [`PartsRGB()`](../../syscall语义数据库/syscall含义详解/20_Parts.md:319) | 否 |
| 第 1 个实参含义 | 颜色缓存选择器；`-1` 为广播模板路径 |
| 第 2～4 个实参含义 | 颜色三通道缓存，通常按 `r/g/b` 理解 |
| 单组选择值 | `0..19`、`21..24` |
| `nil` 颜色参数 | 默认 `100` |
| `r == -10` | 固定写入 `15,20,25` |
| 真正执行 Graph/Parts 颜色应用的函数 | [`f_00060795()`](Sakura_hcb_ir/Sakura/f_00060795.lua:4022) |
| 仅调用 [`f_00069F71()`](Sakura_hcb_ir/Sakura/f_00069F71.lua:1) 能否即时改变现有立绘颜色 | **按原作证据保守判断：不行** |
| 写缓存后再调用刷新链是否可能 | 技术上可能，但属于组合调用，不是单函数能力 |
